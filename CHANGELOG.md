Résumé par version, en français puis `### English` (partie anglaise obligatoire depuis 0.219.0) ; la partie anglaise sert aussi de corps
aux commits et aux notes de release sur GitHub. Preuves citées : docs/evidence/.

## 0.1194.0
- Plan global, X-01 : Lourdeurs, C1.3 : la racine de la fuite des instances déchargées est trouvée et corrigée (X-01). Les relevés des versions 0.1187 à 0.1192 l'ont nommée : une fois tout le reste vidé, il ne restait de vivant que la fenêtre, le cache de données et la fermeture extérieure du constructeur, et les trois pendent d'un seul champ statique. `MainWindow.RaphaelSequences` (le cache des séquences de Raphael, partagé par le carnet d'artisanat et le simulateur) est statique, et la fenêtre le configurait avec le cache de données et avec la durée de garde des calculs, une lambda qui lit ses réglages, donc un délégué sur la fenêtre. Un champ statique vit autant que son contexte de chargement, qui reste vivant dans le processus du jeu (preuve docs/evidence/0.1187-unload-roots.md, section 1) : chaque instance déchargée restait entière en mémoire derrière ce champ (fenêtre, services, catalogues), d'où le tas et les collectes complètes qui grandissaient avec le rang du rechargement. Au déchargement, ce cache oublie maintenant la fenêtre et le cache de données (`RaphaelSequenceCache.Forget`, appelé par `MainWindow.ForgetInstance` avec les autres accroches statiques, en dernier) ; un calcul encore en cours se poursuit sans le disque. Test de comportement : configuré par une instance, le champ statique garde la fenêtre et le cache vivants ; une fois oubliés, les deux sont collectés. Un cliquet refuse un autre objet statique d'une classe qui se configure avec un cache, et la ligne « static » de la mesure dit ce qu'un tel objet tient un niveau plus bas (elle l'avait listé parmi quarante tables de données). Gain supposé tant que la mesure en jeu ne l'a pas montré : deux rechargements après cette version, la ligne « Earlier instance » de l'avant-dernière instance doit tomber de 463 parties vivantes sur 471 à quelques-unes.
- Tests : RaphaelStatic1194Tests. Verify.ps1 (agent) : 2097/2097, 0 avertissement, 0 erreur ; DLL 0.1194.0.0. Non validé en jeu.
### English
- Slowness, C1.3: the root of the leak of unloaded instances is found and fixed (X-01). The readings of versions 0.1187 to 0.1192 named it: once everything else was emptied, only the window, the data cache and the constructor's outer closure stayed alive, and the three hang from one static field. `MainWindow.RaphaelSequences` (the cache of Raphael's sequences, shared by the crafting log and the simulator) is static, and the window configured it with the data cache and with how long the calculations are kept, a lambda that reads its settings, so a delegate on the window. A static field lives as long as its load context, which stays alive in the game process (evidence docs/evidence/0.1187-unload-roots.md, section 1): each unloaded instance stayed whole in memory behind this field (window, services, catalogues), hence the heap and the full collections that grew with the reload's rank. At unload, this cache now forgets the window and the data cache (`RaphaelSequenceCache.Forget`, called by `MainWindow.ForgetInstance` with the other static hooks, last); a calculation still running goes on without the disk. Behaviour test: configured by an instance, the static field keeps the window and the cache alive; once forgotten, both are collected. A cliquet refuses another static object of a class that is configured with a cache, and the measure's « static » line says what such an object holds one level down (it had listed it among forty tables of data). Assumed gain until the measure in the game has shown it: two reloads after this version, the « Earlier instance » line of the instance before the newest should fall from 463 of 471 parts alive to a few.
