## 0.1857.0
- Plan global, X-851 : Relecture du bloc 0.1853 à 0.1854, mineur M1 : un zip « cache » abîmé pour de bon (pas un zip, entrée abîmée, méthode de compression inconnue) empêchait la marque du passage de 0.1854 pour toujours : à chaque chargement, tous les zip « cache » de Backups étaient relus jusqu'à ce que ce zip sorte des cinq gardés ; une méthode de compression inconnue (NotSupportedException) sortait même du passage, laissait les zip suivants et revenait en avertissement à chaque chargement. Maintenant, un zip abîmé est laissé tel quel (personne ne peut le lire), compté et dit une fois dans le journal ; il n'arrête pas les zip suivants et n'empêche pas la marque. Seul un zip tenu par un autre programme laisse le passage au chargement suivant, comme avant. Tests : DamagedCacheZip1855Tests (comportement sur de vrais fichiers : faux zip et zip à méthode inconnue laissés à l'octet près, zip lisible d'après nettoyé, marque écrite, rien de relu ensuite ; zip tenu à côté d'un zip abîmé : pas de marque, nettoyé au chargement suivant).
- Tests : DamagedCacheZip1855Tests. Verify.ps1 (agent) : 4099/4099, 0 avertissement, 0 erreur ; DLL 0.1857.0.0. Rien à essayer en jeu.
### English
- Review of the block 0.1853 to 0.1854, minor M1: a « cache » zip damaged for good (not a zip, a broken entry, an unknown compression method) kept the mark of the 0.1854 pass away for ever: at each load, every « cache » zip of Backups was read again until that zip left the five kept; an unknown compression method (NotSupportedException) even left the pass, skipped the zips after it and came back as a warning at each load. Now a damaged zip is left as it is (nothing can read it), counted and said once in the log; it does not stop the zips after it nor keep the mark away. Only a zip held by another program leaves the pass to the next load, as before. Tests: DamagedCacheZip1855Tests (behaviour on real files: a fake zip and a zip with an unknown method left byte for byte, the readable zip after them cleaned, mark written, nothing read again; a held zip beside a damaged one: no mark, cleaned at the next load).

## 0.1853.0
- Plan global, X-844 : Relecture du bloc 0.1840 à 0.1844, M2 : le balayage des historiques du chat des autres personnages (X-836 M3) ne réécrit plus un fichier pendant qu'un second client le joue. Chaque historique a son fichier de verrou partagé par tous les clients du profil (« N.jsonl.lock », FairFileLock comme les listes et les outils) : les lignes ajoutées, le fichier allégé, une écriture reprise (« désactivé » pendant une écriture) et le balayage le tiennent. Le balayage ne prend le verrou que s'il est libre (un client qui écrit ce fichier : laissé pour le prochain chargement) et relit l'âge du fichier une fois le verrou pris ; un client qui commence à écrire pendant le balayage attend le verrou (2 s au plus, sinon ses lignes restent pour l'écriture suivante) et ses lignes s'ajoutent au fichier balayé. Avant, les lignes ajoutées entre la lecture et le remplacement du fichier étaient perdues. Le verrou d'un historique supprimé part avec lui ; « Effacer l'historique » retire aussi les verrous libres. Tests : ChatSweepLock1853Tests (comportement sur de vrais fichiers : un second client écrit pendant que le balayage allège, puis supprime le fichier, ses lignes gardées ; fichier dont le verrou est tenu laissé entier puis balayé une fois libre ; écriture refusée sans rien perdre quand le verrou reste pris, écriture reprise sous le verrou).
- Tests : ChatSweepLock1853Tests. Verify.ps1 (agent) : 4088/4088, 0 avertissement, 0 erreur ; DLL 0.1853.0.0. Rien à essayer en jeu.
### English
- Review of the block 0.1840 to 0.1844, M2: the sweep of the other characters' chat histories (X-836 M3) no longer rewrites a file while a second client plays that character. Each history has a lock file shared by every client of the profile (« N.jsonl.lock », FairFileLock like the lists and the tools): lines added, the file trimmed, a write taken back (« off » during a write) and the sweep hold it. The sweep takes the lock only when it is free (a client writing that file: left for the next load) and reads the file's age again once the lock is held; a client that starts writing during the sweep waits for the lock (2 s at most, otherwise its lines stay for the next write) and its lines are added to the swept file. Before, the lines added between the file read and the file replaced were lost. The lock of a deleted history goes with it; « Erase the history » also removes the free locks. Tests: ChatSweepLock1853Tests (behaviour on real files: a second client writes while the sweep trims, then deletes the file, its lines kept; a file whose lock is held left whole then swept once free; a write refused without losing anything while the lock stays held, a write taken back under the lock).
