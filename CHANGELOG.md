## 0.1831.0
- Plan global, X-829 : Revue de sécurité avant l'alpha (X-810), I1 : trois sortes de découvertes (lieu notoire inscrit, météo d'une prise, météo d'avant une prise) gardaient la minute d'Éorzéa de l'observation ; elle partait dans le gist avec le jour et la météo, et situait le moment réel à quelques secondes près (une minute d'Éorzéa dure environ 2,9 s). L'avertissement du premier partage et l'aide du bouton de connexion disent l'heure d'Éorzéa (en et fr). - Tests : EorzeaHour1831Tests. Verify.ps1 (agent) : 4025/4025, 0 avertissement, 0 erreur ; DLL 0.1831.0.0. Rien à essayer en jeu.
### English
- Security review before the alpha (X-810), I1: three kinds of discoveries (a vista registered, a catch's weather, the weather before a catch) kept the Eorzea minute of the sighting; it went to the gist with the day and the weather, and told the real moment to a few seconds (an Eorzea minute lasts about 2.9 s). ## 0.1830.0
- Plan global, X-828 : Relecture de 0.1826, constats antérieurs au bloc. M1 (corrigé) : un nouveau gist était créé avant de savoir si github.json s'écrivait ; au premier échange avec ce fichier non inscriptible, le gist était créé puis l'échange s'arrêtait avant le ticket, et si l'état de rotation ne s'écrivait pas non plus (même dossier : disque plein, droits manquants), ce gist restait orphelin et un second était créé après un rechargement. github.json est maintenant écrit juste avant la création d'un nouveau gist : rien n'est créé tant qu'il ne s'écrit pas (« ExchangeMetaUnsaved »). Sans risque pour la connexion d'un autre client (GitHubToken1171, N2) : la même copie est écrite juste après la création, ici quelques instants plus tôt et seulement quand un gist est créé. M2 (écarté, raison) : une ligne abîmée rencontrée par une sauvegarde est réglée tout de suite, sa copie sur le gist n'est pas relue ; avec deux clients du même profil, les observations de l'autre client présentes dans la ligne abîmée manquent au prochain envoi de celui-ci (le texte reste dans facts_aside, l'autre client les garde et les renvoie). Laisser la clé en attente ne corrige pas : la relecture ajoute la copie (DiscoveryStore.Join), si bien que les observations de ce client, déjà dans la ligne, compteraient deux fois, et elle n'aurait lieu qu'au démarrage suivant, après les envois de la session. La limite est écrite dans le code (le commentaire « toute l'observation de ce client » ne valait qu'avec un seul client). Tests : MetaUnsaved1825Tests (premier cas : aucun gist créé tant que github.json ne s'écrit pas, puis un seul gist et un ticket) ; ReviewOld1830Tests (câblage).
- Tests : ReviewOld1830Tests. Verify.ps1 (agent) : 4022/4022, 0 avertissement, 0 erreur ; DLL 0.1830.0.0. Rien à essayer en jeu.
### English
- Review of 0.1826, findings from before the block. M1 (fixed): a new gist was made before knowing whether github.json could be written; at the first exchange with that file unwritable, the gist was made then the exchange stopped before the issue, and if the rotation's state could not be written either (the same folder: disk full, no rights), that gist was left behind and a second one made after a reload. github.json is now written right before a new gist is made: nothing is made while it cannot be (« ExchangeMetaUnsaved »). Safe for another client's sign-in (GitHubToken1171, N2): the same copy is written right after the gist is made, here a few moments earlier and only when a gist is made. M2 (set aside, with its reason): a damaged row met by a save is settled at once, its copy on the gist not read back; with two clients of one profile, the other client's sightings in the damaged row are missing from this client's next send (the text stays in facts_aside, the other client keeps them and sends them again). Leaving the key unsettled does not fix it: the read-back adds the copy (DiscoveryStore.Join), so this client's sightings, already in the row, would count twice, and it would only come at the next start, after the session's sends. The limit is written in the code (the comment « this client's whole fact » held with one client only). Tests: MetaUnsaved1825Tests (first case: no gist made while github.json cannot be written, then one gist and one issue); ReviewOld1830Tests (wiring).

## 0.1829.0
- Plan global, X-827 : Relecture de 0.1826, constat mineur M3. La fusion de confiance (tools/discoveries-trust.py) listait community-discoveries/players et v3 par l'API « contents » de GitHub, qui ne liste que 1 000 éléments d'un dossier : au-delà de 1 000 fichiers joueurs, la base rejouée et la tête de la PR étaient lues tronquées, et chaque fusion automatique devenait un doute commenté en public. folder_blobs passe maintenant par l'API des arbres git (git/trees), dossier par dossier depuis l'arbre du commit, sans cette limite ; un arbre que GitHub dit tronqué, un lien ou un dossier là où sync écrit des fichiers : refusés (jamais de fusion sur une liste partielle). Le faux GitHub des essais de bout en bout répond aussi par les arbres. Auto-test 87/87 (1 201 fichiers joueurs listés avec leur blob, arbre tronqué, lien, dossier, dossier absent). Vérifié contre GitHub : Devloppement et la branche de la PR #54 listés (34 fichiers chacun) ; essai à blanc de la PR #54 : toutes les vérifications de contenu passent, seule sa CI (antérieure à 0.1827) reste rouge.
- Tests : TreesListing1829Tests. Verify.ps1 (agent) : 4021/4021, 0 avertissement, 0 erreur ; DLL 0.1829.0.0. Rien à essayer en jeu.
### English
- Review of 0.1826, minor finding M3. The trusted merge (tools/discoveries-trust.py) listed community-discoveries/players and v3 through GitHub's contents API, which lists at most 1 000 entries of a folder: past 1 000 player files, the base replayed and the pull request's head were read cut short, and every automatic merge became a doubt commented in public. folder_blobs now goes through the git trees API (git/trees), folder by folder from the commit's tree, without that bound; a tree GitHub says is truncated, a link or a folder where sync writes files: refused (never a merge on a partial list). The made-up GitHub of the end-to-end cases answers through trees too. Selftest 87/87 (1 201 player files listed with their blob, truncated tree, link, folder, missing folder). Checked against GitHub: Devloppement and PR #54's branch listed (34 files each); dry run of PR #54: every content check passes, only its CI (from before 0.1827) stays red.
