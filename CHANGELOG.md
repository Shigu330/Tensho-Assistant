### English
- GitHub exchange, GitHub App preparation (X-175, first part): one switch (Discoveries/GitHubSignIn.cs) between today's OAuth app (gist and public_repo scopes) and a GitHub App with least permissions (issues of this repository only, the player's gists), whose client id is still empty: while it is, nothing changes. ## 0.1137.0
- Plan global, X-174 : Échange des découvertes, format v3 (X-174, DEC-052 qui remplace DEC-042 sur le format) : le fichier commun devient community-discoveries/v3/, un index.json et un fichier kind-NN.jsonl.gz par sorte (JSON par lignes, compressé), chacun avec son empreinte SHA-256 et sa taille. Le plugin lit d'abord l'index, ne télécharge que les sortes dont l'empreinte a changé, vérifie empreinte et taille avant de lire, lit en flux avec des bornes (32 Mo compressés, 256 Mo décompressés, 64 Ko par ligne, 200 000 faits par sorte) ; une ligne mauvaise est écartée et comptée, plus de 5 % refusent le fichier ; l'empreinte d'une sorte n'est notée qu'une fois ses faits enregistrés (règle de X-166). Tant que v3 manque ou ne se lit pas, l'ancien discoveries.json (v2) est lu comme avant. Le gist du joueur devient lui aussi un index et un fichier par sorte (construits de ce que vous avez relevé, X-167) ; l'ancien fichier unique en est retiré au premier envoi. L'outil de fusion lit les gists v2 et v3, reconstruit v2 et v3 (sortie identique pour les mêmes faits ; auto-test 25 cas) ; le jeu v3 du dépôt est construit depuis le ticket n° 43 (24 sortes, 1 967 faits). README des découvertes, SECURITY.md et DECISIONS dans les deux moitiés.
- Tests : ExchangeV31137Tests. Verify.ps1 (agent) : 1892/1892, 0 avertissement, 0 erreur ; DLL 0.1137.0.0. Non validé en jeu.
### English
- Discoveries exchange, v3 format (X-174, DEC-052 replacing DEC-042 on the format): the common file becomes community-discoveries/v3/, an index.json and one kind-NN.jsonl.gz file per kind (JSON lines, compressed), each with its SHA-256 hash and size. The plugin reads the index first, downloads only the kinds whose hash changed, checks hash and size before reading, reads as a stream within bounds (32 MB compressed, 256 MB decompressed, 64 KB per line, 200,000 facts per kind); a bad line is left out and counted, more than 5 % refuse the file; a kind's hash is noted only once its facts are saved (X-166 rule). While v3 is missing or unreadable, the old discoveries.json (v2) is read as before. The player's gist also becomes an index and one file per kind (built from what you read yourself, X-167); the old single file is removed from it at the first upload. The merge tool reads v2 and v3 gists and rebuilds both v2 and v3 (same bytes for the same facts; self-test 25 cases); the repository's v3 set is built from issue 43 (24 kinds, 1,967 facts). Discoveries README, SECURITY.md and DECISIONS in both halves.

## 0.1136.0

Le cache des données téléchargées reste en fichiers : l'essai y montre SQLite plus lent (choix provisoire D-140). Bibliothèques Microsoft.Data.Sqlite 10.0.14 et SQLitePCLRaw 2.1.14 (SQLite 3.54, e_sqlite3.dll native à côté de la DLL ; versions au-dessus de celles signalées vulnérables), déclarées dans README et SECURITY.md, portées par le paquet et l'application de bureau. Suite de 0.1133 : un fait relevé avant que sa sorte partagée soit lue est de nouveau joint à la copie partagée, ses imports gardés.

### English
- Discoveries in SQLite (X-172, the user's choice of 12/11). A trial first (report in the X-172 evidence, tool tools/SqliteTrialProbe) at 100,000 and 1 million facts: a save of 1,000 changes takes 0.07 to 0.1 s instead of 0.7 to 4 s (whole files written again), with 18 MB of memory instead of 164 MB to 1.5 GB; the file is almost half the size; a full read is as fast; no damage over 20 hard stops; a read by another process (the desktop application) no longer makes the game's saves fail; no 64 MB bound any more. The discoveries are therefore now in Discoveries.db: one row per fact, only the changed rows written, in one transaction; a failure keeps the changes to write. Si la copie échoue, rien n'est retiré. Un fichier en cours d'utilisation qui ne peut pas être retiré est compté et le message le dit (« vidé en partie »).
- Tests : CacheClear1122Tests. Verify.ps1 (agent) : 1849/1849, 0 avertissement, 0 erreur ; DLL 0.1122.0.0. Non validé en jeu.
### English
- Safer saves, part two (audit A05): « Empty the cache » takes the backup copy and the purge as one operation of the cache's write queue: the copy holds every write asked before, the purge follows with no read nor write in between, and a write asked meanwhile waits then stays after the purge (it is no longer lost nor erased). If the copy fails, nothing is removed. A file in use that cannot be removed is counted and the message says so (« emptied in part »).

## 0.1118.0
- Plan global, X-141 : Banque d'inventaire à deux clients (audit A02) : deux jeux lancés sur le même profil Dalamud partagent le dossier InventoryBank ; une capture de l'un pouvait effacer les personnages enregistrés par l'autre. Désormais chaque changement ne touche que le personnage concerné : sous un verrou du profil (InventoryBank.lock), son fichier est relu, le stockage lu ou oublié y est mis, puis il est réécrit ; ce que l'autre client a enregistré reste. Un personnage n'est effacé que par « Effacer ce personnage ». Le découpage de l'ancien fichier commun et la lecture au démarrage passent par le même verrou. Si l'autre client garde le verrou trop longtemps, l'enregistrement échoue sans rien écrire et le dit.
- Tests : BankShared1118Tests. Verify.ps1 (agent) : 1835/1835, 0 avertissement, 0 erreur ; DLL 0.1118.0.0. Non validé en jeu.
### English
- Inventory bank with two clients (audit A02): two games started on the same Dalamud profile share the InventoryBank folder; a capture by one could erase the characters saved by the other. Now every change touches only the character concerned: under a lock of the profile (InventoryBank.lock), its file is read again, the storage read or forgotten is put in, then it is written back; what the other client saved stays. A character is erased only by « Erase this character ». The split of the former shared file and the load at start use the same lock. If the other client keeps the lock too long, the save fails without writing anything and says so.
