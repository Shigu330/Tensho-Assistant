# Journal des versions / Changelog

Résumé par version, en français puis `### English` (partie anglaise obligatoire depuis 0.219.0) ; la partie anglaise sert aussi de corps
aux commits et aux notes de release sur GitHub. Preuves citées : docs/evidence/.
Chaque version a été compilée et testée par `scripts/Verify.ps1` ; la validation en jeu est indiquée quand l'utilisateur l'a rapportée.
Ce fichier garde la dernière release et les versions qui suivent ; les plus anciennes sont dans [docs/changelog/](docs/changelog/)
(déplacées par `tools/changelog.py archive`, un fichier par centaine de versions).

## 0.1199.0
- Plan global, X-177 : Saccades au chargement, C4.2 : les classes des lecteurs sont compilées sur un fil à part, et chaque lecteur démarre une fois sa classe compilée (X-177). La version 0.1198 compilait chaque classe à l'abonnement, sur le fil qui construit le plugin : mesuré au rechargement suivant, 3 premiers passages lents au lieu de 19 (197 ms d'images au lieu de 2141 ms), mais un chargement de 5,6 s au lieu de 2,4 s (« Readers compiled ahead: 88 classes, 1839 methods in 4353 ms on the loading thread »). Désormais `Diagnostics.ReaderCompiler` compile les classes sur son propre fil, dans l'ordre des abonnements, une classe à la fois et chacune une fois ; chaque façon de s'abonner (`Add`, `AddBoard`, `AddAlways`) prend le ticket de la classe du lecteur, et le lecteur n'est appelé qu'une fois le ticket prêt : classe compilée, ou délai de garde de 15 s passé (le lecteur compile alors lui-même ce qu'il lui faut, comme avant), ou compilateur arrêté. Au déchargement, le fil est prévenu et attendu (au plus une méthode en cours), les lecteurs encore en attente sont lâchés, et le compilateur est oublié avec les accroches statiques. Les lecteurs toujours actifs (`AddAlways`) passent par un rappel gardé avec les autres, et un passage lent de l'un d'eux est nommé comme les autres en mode développeur. Mesure, mode développeur, dix secondes après le chargement : « Readers compiled on their own thread: N classes, M methods in T ms, the last one ready D ms after the first subscribed; W still waiting ». Effet sur « Load created » à lire au prochain chargement : non mesuré en jeu à l'écriture de cette entrée.
- Pour les joueurs : Moins de saccades dans les premières secondes après le chargement ou la mise à jour du plugin.
- Tests : ReaderStart1199Tests. Verify.ps1 (agent) : 2116/2116, 0 avertissement, 0 erreur ; DLL 0.1199.0.0. Rien à essayer en jeu.
### English
- Stutters at load, C4.2: the readers' classes are compiled on a thread of their own, and each reader starts once its class is compiled (X-177). Version 0.1198 compiled each class at subscription, on the thread that builds the plugin: measured at the next reload, 3 slow first passes instead of 19 (197 ms of frames instead of 2141 ms), but a load of 5.6 s instead of 2.4 s (« Readers compiled ahead: 88 classes, 1839 methods in 4353 ms on the loading thread »). From now on `Diagnostics.ReaderCompiler` compiles the classes on its own thread, in the order of the subscriptions, one class at a time and each once; every way to subscribe (`Add`, `AddBoard`, `AddAlways`) takes the ticket of the reader's class, and the reader is called only once the ticket is ready: class compiled, or the guard delay of 15 s over (the reader then compiles what it needs itself, as before), or compiler stopped. At unload, the thread is told and joined (one method at most under way), the readers still waiting are let go, and the compiler is forgotten with the static hooks. The always-on readers (`AddAlways`) go through a guarded wrapper kept with the others, and a slow pass of one of them is named like the others in developer mode. Measure, developer mode, ten seconds after the load: « Readers compiled on their own thread: N classes, M methods in T ms, the last one ready D ms after the first subscribed; W still waiting ». Effect on « Load created » to read at the next load: not measured in the game when this entry was written.
- For players: Fewer stutters in the first seconds after the plugin loads or updates.

### English
- Stutters at load, C4.2: a reader's code is compiled when it subscribes, off the game's thread (X-177). At a reload, the first pass of each reader took 125 to 276 ms of one frame (MapLiveReader, ReadingCapture, ItemDiscoveryWatcher, MapLocalIndexLoader, BankInventoryBridge, AlarmService; ReminderDtrEntry 189 ms according to Dalamud): its code was compiled the first time it ran, on the game's thread. ## 0.1197.0
- Plan global, X-182 : Découvertes : la conversion vers la base SQLite ne peut plus échouer ni perdre une partie de la base quand deux clients convertissent ensemble ou qu'un autre programme tient un fichier un instant (X-182). Le test « deux conversions à la fois » avait échoué une fois sur un fichier « in use » : il avait raison. Une conversion rangeait Discoveries.json pendant que l'autre le lisait ; le déplacement échouait, la base déjà en place, et le plugin y lisait une base impossible à ouvrir : rien n'était enregistré de la session. Pire, un fichier tenu un instant était lu comme abîmé puis renommé « .broken » dès qu'il était lâché, et une base vide était convertie à sa place ; un fichier partagé tenu était laissé hors de la base, puis rangé. Désormais : un fichier parti pendant sa lecture (l'autre client l'a rangé) n'est plus là, sans alerte ; un fichier tenu (violation de partage, accès refusé) n'est ni signalé abîmé ni renommé, et rien n'est converti d'une partie de la base : le prochain démarrage reprend ; un fichier d'avant qui ne peut pas être rangé tout de suite reste à sa place, dit au journal, et le prochain démarrage le range ; la base temporaire est déplacée avec quelques essais si elle est tenue, jamais par-dessus une base en place, et ses restes sont retirés sans erreur, puis à chaque démarrage une fois vieux d'une demi-heure. Tests rendus déterministes sans rien retirer de ce qu'ils prouvent : chaque course est rejouée à la main, sans horloge (poignée tenue comme l'autre programme la tient, arrêt entre la base temporaire et sa mise en place) ; les deux conversions en parallèle tournent 20 fois ; « un autre lecteur lit pendant que le jeu écrit » (0.1136, « reads 4 » sur une machine lente) ne compte plus les lectures de deux secondes : lecture au milieu d'une écriture non validée, puis 40 sauvegardes sous lecture continue, aucune refusée. Preuve de X-01 complétée : l'instance de 0.1195, relue au chargement de 0.1196, « 0 of 1692 parts alive ».
- Pour les joueurs : Découvertes : quand deux clients du jeu démarrent ensemble, ou qu'un autre programme tient un instant un fichier de découvertes, le passage unique vers la nouvelle base n'empêche plus d'enregistrer les découvertes de la session.
- Tests : ConversionRaces1197Tests. Verify.ps1 (agent) : 2105/2105, 0 avertissement, 0 erreur ; DLL 0.1197.0.0. Rien à essayer en jeu.
### English
- Discoveries: the conversion to the SQLite database can no longer fail nor lose a part of the base when two clients convert together or another program holds a file for an instant (X-182). The test « two conversions at once » had failed once on a file « in use »: it was right. One conversion moved Discoveries.json aside while the other read it; the move failed, the database already in place, and the plugin read that as a database it could not open: nothing of the session was saved. Worse, a file held for an instant was read as damaged, then renamed « .broken » as soon as it was let go, and an empty base was converted in its place; a shared file held was left out of the database, then set aside. From now on: a file gone while it is read (the other client set it aside) is not there, without an alert; a file held (sharing violation, access refused) is neither reported as damaged nor renamed, and nothing is converted from a part of the base: the next start tries again; a file of before that cannot be set aside at once stays where it is, said in the log, and the next start sets it aside; the temporary database is moved with a few attempts when it is held, never over a database in place, and its leftovers are removed without an error, then at every start once half an hour old. Tests made deterministic without taking away anything they prove: each race is replayed by hand, without a clock (a handle held as the other program holds it, a stop between the temporary database and its move into place); the two conversions in parallel run 20 times; « another reader reads while the game writes » (0.1136, « reads 4 » on a slow machine) no longer counts the reads of two seconds: a read in the middle of an uncommitted write, then 40 saves under continuous reading, none refused. Evidence of X-01 completed: the instance of 0.1195, read again when 0.1196 loaded, « 0 of 1692 parts alive ».
- For players: Discoveries: when two game clients start together, or another program holds a discoveries file for an instant, the one-time move to the new database no longer keeps the session's discoveries from being saved.
