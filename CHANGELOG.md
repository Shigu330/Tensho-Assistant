# Journal des versions / Changelog

## 0.1309.0
- Plan global, X-310 : Verrou du profil équitable (X-310, test « Bank SQLite 1149 : two clients… » tombé une fois sur la CI, run 43546325155 : « Bank save failed: The bank lock (InventoryBank.lock) is held by another program ») : la cause était une vraie famine entre deux clients du jeu, pas un test fragile. Le verrou du profil était un fichier ouvert sans partage, essayé toutes les 50 ms : le client qui enchaînait ses sauvegardes le relâchait et le reprenait quelques microsecondes plus tard, l'autre tombait presque toujours pendant qu'il était tenu et voyait sa sauvegarde refusée après 10 s (lecture de la banque non gardée). Nouveau FairFileLock (source commune) : un client dont le premier essai échoue laisse une marque d'attente à côté du verrou (« nom.wait-guid.lock », fermée et effacée quand il obtient le verrou ou renonce, effacée par Windows si le processus s'arrête ; une marque de plus de 60 s est ignorée), et un client qui va prendre le verrou laisse d'abord passer les clients marqués (la moitié de son attente au plus, jamais un refus de plus). La banque (PerCharacterBankStore.Locked) et les prix vus (SeenPrices, même verrou interrogé) s'en servent ; la marque finit par .lock, le lien vers l'application de bureau n'envoie rien pour elle. Test de comportement FairLock1309 (5) : un client en boucle serrée et un client qui attend, sur le verrou et sur deux vraies banques partageant un fichier de données (sans l'équité, ces deux tests échouent avec la même exception que la CI) ; marques jamais laissées ; marque périmée ignorée. Le test 1149 passe 20 fois de suite.
- Pour les joueurs : Deux clients du jeu sur un même profil : une sauvegarde de la banque ou des prix n'est plus refusée pendant que l'autre client enregistre à la suite.
- Tests : FairLock1309Tests. Verify.ps1 (agent) : 2435/2435, 0 avertissement, 0 erreur ; DLL 0.1309.0.0. Rien à essayer en jeu.
### English
- Fair profile lock (X-310, the test « Bank SQLite 1149: two clients… » failed once on CI, run 43546325155: « Bank save failed: The bank lock (InventoryBank.lock) is held by another program »): the cause was real starvation between two game clients, not a flaky test. The profile's lock was a file opened without sharing, tried every 50 ms: the client saving in a row released it and took it again microseconds later, the other almost always tried while it was held and had its save refused after 10 s (the bank reading not kept). New FairFileLock (one source): a client whose first try fails leaves a waiting mark beside the lock (« name.wait-guid.lock », closed and deleted when it gets the lock or gives up, deleted by Windows if the process ends; a mark older than 60 s is ignored), and a client about to take the lock first lets the marked clients go (half its wait at most, never one more refusal). The bank (PerCharacterBankStore.Locked) and the seen prices (SeenPrices, the same polled lock) use it; the mark ends in .lock, the link to the desktop application sends nothing for it. Behaviour test FairLock1309 (5): a client in a tight loop and a client that waits, on the lock and on two real banks sharing one data file (without fairness, both fail with the same exception as CI); marks never left behind; a stale mark ignored. Test 1149 passes 20 times in a row.
- For players: Two game clients on one profile: a bank or market save is no longer refused while the other client saves in a row.
