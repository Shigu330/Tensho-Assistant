## 0.1869.0
- Plan global, X-863 : Relecture 0.1868, constat mineur M1. Depuis 0.1867, le verrou partagé (FairFileLock) prenait pour « en attente de suppression » tout fichier dont même la lecture est refusée : un verrou bien présent dont les droits (ACL) refusent lecture et écriture était donc « occupé » sans fin (la banque réessayait toutes les 5 s en attendant « qu'un autre programme la libère »), au lieu d'un échec de chargement clair. Windows dit pourtant la différence : une ouverture qui ne demande qu'à lire les attributs reçoit STATUS_DELETE_PENDING pour un fichier en attente de suppression, et réussit ou reçoit STATUS_ACCESS_DENIED pour un fichier refusé par ses droits (Win32 ramène les deux au même « accès refusé »). DeletePending lit maintenant ce statut (NtOpenFile) ; un fichier disparu compte toujours comme « pas encore » ; hors de Windows, seul un fichier disparu. Le commentaire de Hold est rendu exact. Pas de perte de données avant comme après (rien n'est écrit tant que le chargement n'a pas réussi). Tests de comportement : un verrou refusé par ses droits n'est pas « en attente de suppression » et, passé l'attente, donne « accès refusé », jamais « occupé » ; la banque dont le verrou est refusé échoue clairement au chargement (pas « occupé ») et refuse ensuite d'écrire ; un verrou vraiment en attente de suppression reste reconnu, même quand ses droits refusent la lecture. Tests : DeletePending1869Tests (3), DeletePending1867Tests.
- Tests : DeletePending1869Tests. Verify.ps1 (agent) : 4124/4124, 0 avertissement, 0 erreur ; DLL 0.1869.0.0. Rien à essayer en jeu.
### English
- Review 0.1868, minor finding M1. Since 0.1867 the shared lock (FairFileLock) took for « delete pending » any file that even refuses a read: a lock really there whose rights (ACL) refuse reading and writing was therefore « busy » for ever (the bank tried again every 5 s, waiting for « another program to let it go »), instead of a clear failed load. Windows does tell them apart: an open that only asks to read the attributes gets STATUS_DELETE_PENDING for a file being deleted, and succeeds or gets STATUS_ACCESS_DENIED for a file refused by its rights (Win32 maps both to the same « access denied »). DeletePending now reads that status (NtOpenFile); a file that is gone still counts as « not yet »; outside Windows, only a file that is gone. The comment in Hold is made exact. No data loss before or after (nothing is written until the load succeeded). Behaviour tests: a lock refused by its rights is not « delete pending » and, past the wait, raises access denied, never busy; the bank whose lock is refused fails its load clearly (not busy) and then refuses to write; a lock really « delete pending » is still told apart, also when its rights refuse a read. Tests: DeletePending1869Tests (3), DeletePending1867Tests.

Tests de comportement DeletePending1867Tests : verrou laissé en attente de suppression au-delà de l'attente (exception « occupé » avec le refus de Windows dedans), banque dans ce cas (BankLockBusyException, puis chargement et écriture une fois le fichier relâché), verrou en lecture seule (accès refusé).
- Tests : DeletePending1867Tests. Verify.ps1 (agent) : 4119/4119, 0 avertissement, 0 erreur ; DLL 0.1867.0.0. Rien à essayer en jeu.
### English
- Review 0.1866, earlier finding M2: since 0.1865 a « delete pending » lock file is « not yet » during the wait, but the last open, once the wait was over, let the access denied through as it was. Callers that tell « busy » from « failed » took it for a hard failure: the bank marked its load as failed and refused every write until a reload, instead of trying again as for a held lock. FairFileLock.Hold now gives the caller's « busy » exception when the file is still delete pending after the wait; that case is told by an open for reading, with every sharing allowed, being refused too (the file's attributes stay readable and do not tell). A file really there that refuses writing (read only) still raises access denied. Behaviour tests DeletePending1867Tests: a lock left delete pending past the wait (the « busy » exception, with Windows' refusal inside), the bank in that case (BankLockBusyException, then load and save once the file is let go), a read-only lock (access denied).
