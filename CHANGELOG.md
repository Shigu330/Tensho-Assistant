# Journal des versions / Changelog

Résumé par version, en français puis `### English` (partie anglaise obligatoire depuis 0.219.0) ; la partie anglaise sert aussi de corps
aux commits et aux notes de release sur GitHub. Preuves citées : docs/evidence/.
Chaque version a été compilée et testée par `scripts/Verify.ps1` ; la validation en jeu est indiquée quand l'utilisateur l'a rapportée.
Ce fichier garde la dernière release et les versions qui suivent ; les plus anciennes sont dans [docs/changelog/](docs/changelog/)
(déplacées par `tools/changelog.py archive`, un fichier par centaine de versions).

## 0.1277.0
- Plan global, X-268 : Outillage (R19.3), suite de 0.1276 : l'essai de 0.1276 (joueur en mission simulé) a montré que le crochet pre-push relançait Verify.ps1 sans option et recompilait là où le jeu charge, donc rechargeait le jeu pendant la mission. Verify.ps1 lit maintenant TENSHO_NORELOAD=1 (posé par la publication quand le joueur est occupé, hérité par git et son crochet) comme -NoReload, jamais pour une release.
- Tests : Reload1276Tests. Verify.ps1 (agent) : 2332/2332, 0 avertissement, 0 erreur ; DLL 0.1277.0.0. Rien à essayer en jeu.
### English
- Tooling (R19.3), follow-up of 0.1276: the trial of 0.1276 (player in a duty, simulated) showed the pre-push hook running Verify.ps1 with no switch and building where the game loads, so reloading the game during the duty. Verify.ps1 now reads TENSHO_NORELOAD=1 (set by the publication while the player is busy, inherited by git and its hook) as -NoReload, never for a release.

## 0.1276.0
- Plan global, X-268 : Outillage (R19.3) : quand le joueur est en mission, en pêche en mer ou en contenu classé, une version se publie quand même sans recharger le jeu : Verify.ps1 -NoReload compile le plugin dans artifacts\noreload\ (propriété TenshoOutputPath du csproj), toutes les vérifications tournent sur cette compilation, et la publication libre suivante recompile là où le jeu charge. Verify.ps1 refuse -Release avec -NoReload (une release est toujours compilée là où le jeu la charge), et une compilation faite à part n'est jamais reprise pour celle du jeu. Côté agent : dernière version d'un relais prête à publier par publish.sh --last, sauvegarde et contexte dits à la fin de chaque version, release et annonce refusées hors de la session maître.
- Tests : Reload1276Tests. Verify.ps1 (agent) : 2331/2331, 0 avertissement, 0 erreur ; DLL 0.1276.0.0. Rien à essayer en jeu.
### English
- Tooling (R19.3): while the player is in a duty, an ocean voyage or competitive content, a version is still published without reloading the game: Verify.ps1 -NoReload builds the plugin into artifacts\noreload\ (csproj property TenshoOutputPath), every check runs on that build, and the next free publish builds again where the game loads it. Verify.ps1 refuses -Release with -NoReload (a release is always built where the game loads it), and a build made beside the game is never taken for the game's one.

## 0.1275.0
- Plan global, X-267 : Outillage (R36) : tous les tests tournent en parallèle, une classe par fil, les classes trouvées seules (plus de liste à tenir dans Program.cs), quarantaine datée et classes [SerialTests] prévues ; Verify.ps1 les lance pendant la publication et le dessin de l'application de bureau (tests : 106 s l'un après l'autre, 16 s en parallèle). Le test fragile « Disk cache survives a new instance… » (CI rouge de 0.1267) est corrigé à la cause : un fichier tenu un instant par un autre programme faisait échouer l'écriture du cache local ; le remplacement est maintenant réessayé (AtomicFile.OverwriteWhenFree, pour le cache et toute écriture atomique). Une course dans un test de l'enregistrement des réglages, révélée par le parallèle, est corrigée. publish.sh refuse un test existant modifié ou retiré, ou un compte de tests en baisse, sans raison écrite (scripts/agent/oracle.py).
- Tests : Parallel1275Tests. Verify.ps1 (agent) : 2330/2330, 0 avertissement, 0 erreur ; DLL 0.1275.0.0. Rien à essayer en jeu.
### English
- Tooling (R36): every test runs in parallel, one class per thread, classes found by themselves (no list to keep in Program.cs any more), dated quarantine and [SerialTests] classes provided; Verify.ps1 runs them while the desktop application is published and drawn (tests: 106 s one after the other, 16 s in parallel). The flaky test « Disk cache survives a new instance… » (red CI of 0.1267) is fixed at its cause: a file held an instant by another program made the local cache's write fail; the replace is now tried again (AtomicFile.OverwriteWhenFree, for the cache and every atomic write). A race in a test of the settings saver, shown by the parallel run, is fixed.

## 0.1274.0
- Plan global, X-264 : X-264, suite (constat du journal du jeu après 0.1269 à 0.1273) : la part « StateBar » de la première image après un chargement était passée d'environ 4 ms à 7 à 11 ms. Cause : depuis les jauges, l'échantillonnage de l'historique était appelé dès la première image, seulement pour ressortir aussitôt (le délai de 20 s du démarrage), mais cet appel faisait compiler son code sur le fil du jeu. Plus rien du tableau de bord n'est appelé avant le délai de démarrage : le battement ressort d'abord. Le tableau de bord ouvert par le joueur lit toujours tout de suite ; l'historique commence toujours 20 s après le chargement. La première image elle-même n'avait pas bougé hors du bruit (186 à 214 ms sur ces versions, 165 à 213 ms avant). Test : DashboardFirstFrame1274Tests.
- Tests : DashboardFirstFrame1274Tests. Verify.ps1 (agent) : 2323/2323, 0 avertissement, 0 erreur ; DLL 0.1274.0.0. Rien à essayer en jeu.
### English
- X-264, follow-up (found in the game's log after 0.1269 to 0.1273): the « StateBar » part of the first frame after a load had gone from about 4 ms to 7 to 11 ms. Cause: since the gauges, the history's sampling was called from the first frame, only to return at once (the 20 s start delay), but that call had its code compiled on the game's thread. Nothing of the dashboard is called before the start delay any more: the tick returns first. The dashboard opened by the player still reads at once; the history still starts 20 s after the load. The first frame itself had not moved beyond the noise (186 to 214 ms on these versions, 165 to 213 ms before). Test: DashboardFirstFrame1274Tests.
