## 0.1797.0
- Plan global, X-784 : Découvertes, mode développeur : « Vider la base » marche de nouveau (X-784, constat I1 de la relecture du bloc 0.1790 à 0.1795). Depuis 0.1794, le plugin garde Discoveries.db ouvert toute la session ; la copie zip prise avant le vidage lisait ce fichier comme un fichier ordinaire (lecture qui refuse un fichier ouvert en écriture ailleurs) et échouait à chaque fois : rien n'était vidé (« nothing was removed »). Maintenant la base entre dans la copie par la copie cohérente de SQLite (VACUUM INTO, une seule transaction de lecture : les dernières sauvegardes encore dans le journal y sont, une sauvegarde en cours y est entière ou pas du tout), écrite à côté puis effacée après lecture ; le journal (-wal) et la mémoire partagée (-shm) restent hors de la copie (restaurés avec une base plus récente, un vieux journal pourrait y être rejoué) ; les deux jetons GitHub restent hors de la copie comme avant. Les autres fichiers d'une copie (celle du cache aussi) sont lus en partage : un fichier tenu ouvert par un autre programme ne fait plus échouer la copie. Nouveau Discoveries/DiscoveryBackup.cs (la copie du bouton). Tests de comportement DiscoveryClear1797Tests (5) sur une vraie base gardée ouverte comme le fait le plugin : l'ancienne copie refusée (le constat reproduit), la nouvelle faite avec tous les faits (ceux du journal compris) et lisible comme une base, ni jeton ni journal dedans, aucun fichier de passage laissé ; fichier tenu ouvert par un autre copié ; sans base, les fichiers copiés comme avant.
- Tests : DiscoveryClear1797Tests. Verify.ps1 (agent) : 3924/3924, 0 avertissement, 0 erreur ; DLL 0.1797.0.0. Non validé en jeu.
### English
- Discoveries, developer mode: « Empty the base » works again (X-784, finding I1 of the review of block 0.1790 to 0.1795). Since 0.1794 the plugin keeps Discoveries.db open for the whole session; the zip copy taken before emptying read that file as a plain file (a read that refuses a file open for writing elsewhere) and failed every time: nothing was emptied (« nothing was removed »). The base now goes into the copy through SQLite's consistent copy (VACUUM INTO, one read transaction: the last saves still in the journal are in it, a save running meanwhile is in it whole or not at all), written beside then deleted once read; the journal (-wal) and the shared memory (-shm) stay out of the copy (restored with a newer base, an old journal could be replayed onto it); both GitHub tokens stay out of the copy as before. The other files of a copy (the cache's too) are read in shared mode: a file another program holds open no longer fails the copy. New Discoveries/DiscoveryBackup.cs (the button's copy). Behaviour tests DiscoveryClear1797Tests (5) on a real base kept open as the plugin does: the former copy refused (the finding reproduced), the new one made with every fact (the journal's included) and readable as a base, no token nor journal in it, no temporary file left; a file held open by another handle copied; without a base, the files copied as before.

### English
- Tests: a raw thread no longer takes the tests' process down (X-783, flaky test seen on 22/11 during relay 177: « tests exit 127 », a trace ending in Thread.StartCallback, not reproduced). Most likely cause found: the greedy client of « Fair lock 1309 » (first case) held the lock on a raw thread without catching its exception; under load, a wait for the lock past 10 s threw there and ended the whole test process (every test with it), where the runner would have kept it for its test. That thread now keeps its exception, checked after the thread ends; so does the thread of « Reader steps 1312 ». ## 0.1794.0
- Plan global, X-750 : Bases SQLite de Tensho gardées ouvertes (X-750, idée I-024 choisie par l'utilisateur le 21/11). Chaque appel ouvrait sa propre connexion (sans réserve de connexions) ; la fermeture de la dernière repliait le journal (WAL) dans le fichier, jusqu'à 1,7 s mesuré sous charge (relais 108). Les connexions restent sans réserve (libération de SQLite au déchargement inchangée). Les essais et les copies de l'application de bureau ne gardent rien ouvert. Mesure dans le journal à chaque chargement : une sauvegarde chronométrée avec le repli du journal (comme chaque sauvegarde d'avant) puis fichier gardé ouvert (« Tensho data: a save took … ms … X-750 ») ; une ligne d'une table save_probe réécrite pour cela. Test « Fair lock 1309 » rendu robuste : il mesurait parfois rien (sauvegardes plus rapides depuis 0.1793) ; son fil ne peut plus faire tomber le processus des tests.
- Tests : KeptOpen1794Tests. Verify.ps1 (agent) : 3912/3912, 0 avertissement, 0 erreur ; DLL 0.1794.0.0. Non validé en jeu.
### English
- Tensho's SQLite databases kept open (X-750, idea I-024 chosen by the user on 21/11). Every call opened its own connection (no pooling); closing the last one folded the journal (WAL) into the file, up to 1.7 s measured under load (relay 108). The plugin now keeps an idle connection open on TenshoData.db (from the start, off the game's thread) and on Discoveries.db (when the discoveries load, off the game's thread): a save's close no longer folds the journal in; SQLite folds it in by itself as saves go (on their thread, never the game's: every save of these files already runs off the game's thread) and at unload (full fold then close, registered first so it is released last, after every family). Connections stay unpooled (SQLite's release at unload unchanged). The tests and the desktop application's copies keep nothing open. Measured in the log at each load: one save timed with the journal folded in (as each save before) then with the file kept open (« Tensho data: a save took … ms … X-750 »); one row of a save_probe table written again for it. Test « Fair lock 1309 » made robust: it sometimes measured nothing (faster saves since 0.1793); its thread can no longer end the test process.
