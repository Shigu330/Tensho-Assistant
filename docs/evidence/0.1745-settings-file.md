# 0.1745: Tensho saves its settings itself (X-685, part 2: Newtonsoft and TypeDescriptor)

English first, then French.

## Why (0.1741, the out-of-game trial)

- Every copy of Tensho unloaded before stayed in the game process (« context alive » in the log). System.Text.Json was the first holder
  (fixed in 0.1741: every options of Tensho has a resolver of its own). The second was the settings: Dalamud saves and reads them with
  Newtonsoft (type names), and Newtonsoft, through TypeDescriptor (System.ComponentModel, shared by the whole process), keeps the types it
  saw in three private tables for good; TypeDescriptor.Refresh does not empty them (docs/evidence/0.1741-unload-json.md).
- The user's choice of 21/11 (D-206 a): Tensho saves its settings itself with System.Text.Json, in a file of its own, reads Dalamud's file
  once, and a no-loss test proves it (R28.14). The other way (emptying the private tables at unload by reflection on the runtime) was left
  aside: fragile, a risk inside the game process.

## What Tensho does (0.1745)

- The file: `%APPDATA%\XIVLauncher\pluginConfigs\TenshoAssistant\Settings.json` (SettingsFile). Dalamud's file
  (`pluginConfigs\TenshoAssistant.json`) is read once, at the first load, then left as it was: an older Tensho still finds its settings.
  Newtonsoft is no longer used by the plugin (a test says so).
- The shape stays Newtonsoft's (SettingsJson): public fields written too (the colours, Vector4), objects and tables already made filled in
  place (Newtonsoft's « Auto »: the map's icon sizes keep a default for an icon absent from the file), names read whatever their case,
  NaN and infinities written as text. Dalamud's file: the « $type » names taken out at any depth, then read the same way.
- Each save, under a lock shared by the game clients of the PC: the file read again and merged three ways with what this client last read
  or wrote: a value it did not change is taken from the file (another client's change, a name a newer Tensho wrote), a value it changed
  is its own, an entry removed stays removed. The file written whole (temporary file, then moved in place); the version before kept as
  `Settings.json.bak`. A write that fails changes nothing on disk, is said once in the log, and the next save writes everything.
- A file that cannot be read is copied aside (`Settings.unreadable-<date>.json`), never written over unseen; then the backup is read,
  then Dalamud's file, then new settings.
- The desktop app reads the new file (the plugin's own reader, through its guard: the Discord addresses taken out), Dalamud's file while
  there is no new one; it still writes nothing. The local link's « settings » notice follows the new file.

## Proofs

- SettingsFile1745Tests: every member of the settings at any depth filled with a value that is not its default (a list item, a table
  entry, at each level; more than 300 members), written by Dalamud's way and read back by the new reader: the same as Newtonsoft reads it;
  the new text reads back to the same settings and the same text; Dalamud's file read once; two clients keep each other's changes (one
  after the other, and 25 saves each at the same time while a reader never sees a half file); a write that fails; names unknown kept at
  the top and inside an object; removals kept; an unreadable file kept aside; a copy of the tests loaded in a context that can unload is
  collected after it read and wrote the settings, and the control (a copy that used Newtonsoft) stays.
- The user's real settings file (78 KB, 230 settings), read on this PC by a test never committed (only its outcome printed): no
  difference between Newtonsoft's reading and the new one; the new text (62 KB) reads back to the same settings and the same text; no name
  unknown to this version.

## The dashboard's « worth a look »

- Read again (X-685 asks it): the memory line of the dashboard has no threshold (always « ok »); « worth a look » comes from another line
  (a reader unavailable, a panel off, a slow page, a suspect self-check). The megabytes the server bar shows are the managed heap of the
  whole game process (GC.GetGCMemoryInfo: Dalamud and every plugin), not Tensho's alone.

## To confirm in game

- At the first load of 0.1745, the log says once « Settings moved from Dalamud's settings file to Tensho's own (Settings.json) »; the
  settings are the same as before (theme, alarms, chat, map).
- After a few reloads, developer mode's « context alive » lines name no copy loaded from 0.1745 on (the copies before it stay: they used
  Newtonsoft), and the managed memory no longer climbs by a copy at each reload.

## Measured in game (21/11, the reloads of 0.1745 and 0.1746)

- 19:55: first load of 0.1745: « Settings moved from Dalamud's settings file to Tensho's own (Settings.json) » once; Settings.json written
  (63 KB); no warning nor error. 20:02 (load 108): read from Settings.json.
- 20:08:54 (load 109, 0.1746): the two copies of 0.1745 (loaded at 19:55:26 and 20:02:45) still say « context alive, 0 of 463 parts
  alive ». In game, something else than Newtonsoft and System.Text.Json still keeps an unloaded copy (out of the game, the test's copy is
  collected): X-685 stays open; the next holder is to be found (what the game process shares with the plugin: Dalamud's services and
  events, the data manager's sheet caches, the runtime's listeners, native callbacks).

# 0.1745 : Tensho enregistre ses réglages lui-même (X-685, partie 2 : Newtonsoft et TypeDescriptor)

L'anglais d'abord, puis le français.

## Pourquoi (0.1741, l'essai hors du jeu)

- Chaque copie de Tensho déchargée restait dans le processus du jeu (« context alive » au journal). System.Text.Json était le premier à
  la garder (corrigé en 0.1741 : chaque jeu d'options de Tensho a son propre résolveur). Le second, les réglages : Dalamud les enregistre
  et les lit avec Newtonsoft (noms de types), et Newtonsoft, par TypeDescriptor (System.ComponentModel, partagé par tout le processus),
  garde pour de bon les types vus dans trois tables privées ; TypeDescriptor.Refresh ne les vide pas (docs/evidence/0.1741-unload-json.md).
- Le choix de l'utilisateur du 21/11 (D-206 a) : Tensho enregistre ses réglages lui-même avec System.Text.Json, dans son propre fichier,
  lit une fois le fichier de Dalamud, et un test de non-perte le prouve (R28.14). L'autre voie (vider les tables privées au déchargement
  par réflexion sur le moteur) est écartée : fragile, un risque dans le processus du jeu.

## Ce que fait Tensho (0.1745)

- Le fichier : `%APPDATA%\XIVLauncher\pluginConfigs\TenshoAssistant\Settings.json` (SettingsFile). Le fichier de Dalamud
  (`pluginConfigs\TenshoAssistant.json`) est lu une fois, au premier chargement, puis laissé tel quel : un Tensho plus ancien retrouve ses
  réglages. Le plugin n'utilise plus Newtonsoft (un test le vérifie).
- La forme reste celle de Newtonsoft (SettingsJson) : champs publics écrits aussi (les couleurs, Vector4), objets et tables déjà faits
  remplis sur place (« Auto » de Newtonsoft : les tailles d'icônes de la carte gardent un défaut pour une icône absente du fichier), noms
  lus quelle que soit leur casse, NaN et infinis écrits en texte. Fichier de Dalamud : les noms « $type » retirés à toute profondeur, puis
  lu de la même façon.
- À chaque enregistrement, sous un verrou partagé par les clients du jeu du PC : le fichier relu et fusionné à trois voies avec ce que ce
  client a lu ou écrit en dernier : une valeur qu'il n'a pas changée est prise du fichier (le changement d'un autre client, un nom écrit
  par un Tensho plus récent), une valeur qu'il a changée est la sienne, une entrée retirée reste retirée. Le fichier écrit en entier
  (fichier temporaire, puis déplacé à sa place) ; la version d'avant gardée en `Settings.json.bak`. Une écriture qui échoue ne change
  rien sur le disque, est dite une fois au journal, et l'enregistrement suivant écrit tout.
- Un fichier illisible est copié à part (`Settings.unreadable-<date>.json`), jamais écrasé sans être vu ; puis la copie de secours est
  lue, puis le fichier de Dalamud, puis des réglages neufs.
- L'application de bureau lit le nouveau fichier (le lecteur du plugin, par sa garde : adresses Discord retirées), le fichier de Dalamud
  tant qu'il n'y a pas le nouveau ; elle n'écrit toujours rien. L'avis « settings » du lien local suit le nouveau fichier.

## Preuves

- SettingsFile1745Tests : chaque membre des réglages, à toute profondeur, rempli d'une valeur autre que sa valeur par défaut (un élément
  de liste, une entrée de table, à chaque niveau ; plus de 300 membres), écrit à la façon de Dalamud et relu par le nouveau lecteur : le
  même que ce que lit Newtonsoft ; le nouveau texte se relit en les mêmes réglages et le même texte ; fichier de Dalamud lu une fois ; deux
  clients gardent les changements l'un de l'autre (l'un après l'autre, et 25 enregistrements chacun en même temps pendant qu'un lecteur ne
  voit jamais un fichier à moitié écrit) ; une écriture qui échoue ; noms inconnus gardés en tête et dans un objet ; retraits gardés ; un
  fichier illisible mis à part ; une copie des tests chargée dans un contexte déchargeable est libérée après avoir lu et écrit les
  réglages, et le témoin (une copie passée par Newtonsoft) reste.
- Le vrai fichier de réglages de l'utilisateur (78 Ko, 230 réglages), lu sur ce PC par un test jamais commité (seul son résultat
  affiché) : aucune différence entre la lecture de Newtonsoft et la nouvelle ; le nouveau texte (62 Ko) se relit en les mêmes réglages et
  le même texte ; aucun nom inconnu de cette version.

## Le « à voir » du tableau de bord

- Relu (X-685 le demande) : la ligne mémoire du tableau de bord n'a pas de seuil (toujours « ok ») ; « à voir » vient d'une autre ligne
  (un lecteur indisponible, un panneau coupé, une page lente, un auto-contrôle douteux). Les mégaoctets de la barre du serveur sont le tas
  géré de tout le processus du jeu (GC.GetGCMemoryInfo : Dalamud et tous les plugins), pas Tensho seul.

## À confirmer en jeu

- Au premier chargement de 0.1745, le journal dit une fois « Settings moved from Dalamud's settings file to Tensho's own
  (Settings.json) » ; les réglages sont les mêmes qu'avant (thème, alarmes, chat, carte).
- Après quelques rechargements, les lignes « context alive » du mode développeur ne nomment aucune copie chargée depuis 0.1745 (celles
  d'avant restent : elles passaient par Newtonsoft), et la mémoire gérée ne monte plus d'une copie à chaque rechargement.

## Mesuré en jeu (21/11, les rechargements de 0.1745 et 0.1746)

- 19 h 55 : premier chargement de 0.1745 : « Settings moved from Dalamud's settings file to Tensho's own (Settings.json) » une fois ;
  Settings.json écrit (63 Ko) ; ni avertissement ni erreur. 20 h 02 (chargement 108) : lu depuis Settings.json.
- 20 h 08 min 54 (chargement 109, 0.1746) : les deux copies de 0.1745 (chargées à 19 h 55 min 26 et 20 h 02 min 45) disent encore
  « context alive, 0 of 463 parts alive ». En jeu, autre chose que Newtonsoft et System.Text.Json garde encore une copie déchargée (hors
  du jeu, la copie du test est libérée) : X-685 reste ouvert ; le détenteur suivant est à trouver (ce que le processus du jeu partage avec
  le plugin : services et événements de Dalamud, caches de feuilles du gestionnaire de données, écouteurs du moteur, rappels natifs).
