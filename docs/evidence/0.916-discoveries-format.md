# 0.916 — discoveries file format, version 2 (X-76 E1, DEC-042)

The discoveries file (local base `Discoveries.json`, exports, gists of the GitHub exchange, `community-discoveries/discoveries.json`) is fixed before 1.0.0.
Version 2 only adds optional fields, so players' files never need a migration: a version 1 file is read as it is, and every file is written as version 2.
Code: `src/TenshoAssistant/Discoveries/DiscoveriesModel.cs` (`DiscoveryFact`, `ValueCounts`, `DiscoveryFile`, `DiscoveryStore`), `CommunityDiscoveries.cs`,
`ItemDiscoveryWatcher.Dalamud.cs`, `tools/discoveries-merge.py`. Tests: `tests/TenshoAssistant.Tests/DiscoveriesFormat916Tests.cs`.

## File

`{"Version":2,"Producer":"…","Written":"…","Facts":[…]}`. Readers accept versions 1 and 2 (`DiscoveryFile.Readable`: the base file, an imported file,
the common file, a gist); any other version is refused, as before.

## Fact

Unchanged: `Kind`, `Subject`, `Detail`, `Territory`, `Map`, `CellX`, `CellZ` (the identity: `Key`, still these seven parts), `X`, `Z`, `LevelMin`, `LevelMax`,
`Seen`, `Imported`, `First`, `Last`, and the computed `Key` the plugin writes.

New, optional, left out of the file when 0 or empty:

| Field | Meaning | Shared in a gist and the common file |
|---|---|---|
| `Hq` | how many of your sightings were HQ (an item got) | yes |
| `Values` | your sightings per value seen: `{"value":count}` (level, quantity, bite time, Eorzea minute, day…) | yes |
| `ImportedHq` | imported HQ sightings: the largest number an imported file gave | no (`CommunityDiscoveries.Mine` clears it) |
| `ImportedValues` | imported values: per value, the largest count an imported file gave | no (cleared the same way) |

Yours and imported ones are kept apart like `Seen` and `Imported`: otherwise each exchange would send the common file's counts back inside your own facts,
and the common file would count them again at every rebuild.

### Histogram bound

- At most 32 values (`ValueCounts.MaxValues`); a value from 0 to 100 000; a count from 1 to 100 000 000.
- Overflow rule: a new value when 32 are already kept is counted under the nearest value kept, the lower one on a tie. No sighting is lost (the total
  stays the number of sightings), the shape stays close, and `LevelMin` / `LevelMax` stay exact.
- Rejected: dropping the rarest value (it loses sightings, so drop rates and HQ shares would go wrong).

### Validity (`DiscoveryStore.Valid`, mirrored in the merge tool)

Histograms within the bound; `Hq` from 0 to the total of `Values`; `ImportedHq` from 0 to the total of `ImportedValues`. A fact that breaks it is refused,
read or imported (and counted in the merge tool's refusals, with the 5 % flag).

## Recording

- `SeeSource`: every sighting counts its value in `Values`; `hq: true` adds one to `Hq`. A value above 100 000 is not noted (it was refused when read before).
- `See` (monsters, hunt marks, FATEs): the level counts in `Values` at each sighting counted in `Seen` (10 minutes or an hour apart); an unknown level (0)
  is not counted.
- HQ passed by the item watcher (`ItemDiscoveryWatcher.Dalamud.cs`):
  - bag gains: the bags now count HQ units apart (`slot.IsHq`); a gain is HQ when HQ units of that item came in. Passed for FishCatch, MonsterDrop,
    FateReward, ItemFromItem and DutyChest (coffers);
  - the loot window (DutyChest), venture rewards and desynthesis results: the raw item id carries the HQ offset (1 000 000 to 1 999 999,
    `ItemGains.IsHq`). The offset is read in the code already (`%1_000_000`) but no HQ case is in an evidence capture yet: not validated in game.
  - Not passed: reductions, submersible drops, quest hand-ins (QuestItemAsked keeps its HQ id in `Subject`, as in 0.911) and the other kinds (not items).

## Merging

| Where | Yours (`Hq`, `Values`) | Imported (`ImportedHq`, `ImportedValues`) |
|---|---|---|
| `DiscoveryStore.Join` (two facts of one cell, when a base is read) | added | added |
| `DiscoveryStore.Merge` (an imported file) | never touched | per value the largest of what is kept and what the file brings (its `Values` and `ImportedValues` added); `ImportedHq` the largest; a file read again adds nothing |
| `tools/discoveries-merge.py rebuild` (one file per player) | added over the players into the common file's `Hq` and `Values` (same bound and overflow rule) | dropped when read (`ImportedHq`, `ImportedValues` are not the player's) |

HQ counts are always held within the total of their histogram (`ValueCounts.AtMostTotal`), so a joined fact never becomes invalid.

## Files rewritten

`python -I tools/discoveries-merge.py rebuild` rewrote `community-discoveries/discoveries.json` as version 2: only `Version` (1 → 2) and `Written` changed,
the 664 facts are identical. `community-discoveries/players/43.json` has no version field and was not rewritten. `check` of the common file:
664 facts, 0 refused.

The merge tool's `CELL` and `MAX_FACTS` were inside the comment of the `KINDS` line (since 0.891), so `check` and `sync` stopped with a NameError;
they are on their own line again.

## Limits

- A plugin before 0.916 refuses a version 2 file (« CommonUnreadable » for the common file read from `main`); the release that brings the version 2 common
  file to `main` brings the plugin that reads it.
- Facts recorded before 0.916 have no `Values`: their earlier sightings are only in `Seen`, `LevelMin`, `LevelMax`.
- Not added: counts per visit (kills per monster, chests per duty, visits per sector: P8). They need no new field: they can be new kinds (a number in `Kind`).
