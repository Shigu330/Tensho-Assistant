# 0.1602: the game's entries in a player's menu of the Tensho chat window (X-654)

The user's request of 20/11 (test T-0.1566-2): the right click on a player in the Tensho chat window should offer what the game's menu offers.
One right click gives both: Tensho's entries (Hide, Put forward) and the game's. The user's choice of 20/11, after the reading of Chat 2
below: « by the game's menu » (the recommended way).

## What the game's library offers (ApiProbe, FFXIVClientStructs of Dalamud 15)

- No function opens the game chat's own player menu: `AgentChatLog` only holds context fields; `AgentContext` builds menus for whoever
  opens them.
- `AgentHUD.OpenContextMenuFromTarget(GameObject*)`: the game's own menu of a character, for a character in the object table (in range).
- The game's identifiers of a message (content id, account id) are not in Dalamud's chat event: they come from the game's log,
  `RaptureLogModule.AddMsgSourceEntry(contentId, accountId, messageIndex, worldId, chatType)`.

## How Chat 2 does it (read to understand, Infiziert90/ChatTwo, EUPL-1.2; nothing copied)

- `Ui/Handler/PayloadHandler.cs` (`DrawPlayerPopup`): its own menu; each entry calls the game on the click.
- `MessageManager.cs`: a hook on `RaptureLogModule.AddMsgSourceEntry` (pointer kept by FFXIVClientStructs) that calls the game first, then
  gives the content and account ids to the message just received (« called immediately after » the chat event, for each message).
- Invite: `InfoProxyPartyInvite` (`InviteToParty` same world, `InviteToPartyContentId` another world); adventurer plate:
  `AgentCharaCard.OpenCharaCard(contentId)`; mute list: `AgentMutelist.Add`; target: the object table.
- Friend request and blacklist: it sends the commands « /friendlist add » and « /blist add » to the chat, the name passed by a hook on a
  signature of its own (not in FFXIVClientStructs): fragile at each patch. Report and Party Finder: not offered.

## What Tensho does (0.1602)

- `Chat/ChatSources` (in memory only, never in the chat history on disk, cleared with the messages, at logout and at unload): the sender's
  name and world from the message's player link, then the game's identifiers from the hook, given only when the game's world is the
  sender's (never to another player). `Chat/ChatPlayerActions`: the hook (pointer checked first), and the entries, each run on the player's
  click only, at the next framework tick with the character loaded (R03.3): tell (`RaptureShellModule.SetContextTellTarget`, the function the
  game's menus call: the typing box set to a tell to that player, nothing sent), reply in the message's mode (tells; say, party and alliance
  through `ChangeChatChannel` with the game's `ChatChannel` values of FFXIVClientStructs), invite, adventurer plate, mute list, target, and
  « Game menu… » for a character in range (`AgentHUD.OpenContextMenuFromTarget`: friend request, blacklist and the rest as the game offers
  them). Friend request and blacklist are not done by a command or a signature (the user's choice). No « Report ».
- Texts: the client's own (`Addon` rows, game 2026.11.03, French and English): 50 « Murmurer » / « Send Tell », 368 « Répondre avec le même
  mode de discussion » / « Reply in Selected Chat Mode », 54 « Inviter dans l'équipe » / « Invite to Party », 15083 « Voir la carte de
  personnage » / « View Adventurer Plate », 14833 « Ajouter à la liste muette » / « Register to Mute List », 8320 « Cibler » / « Target ».
- An entry that needs the identifiers is greyed without them (a message from the history on disk, a line the game gave none for). A failure
  turns the entries off until the plugin reloads, said once in the log (R08).

## « Report this player » (the user's question of 20/11: « why no report? »)

Probe of FFXIVClientStructs (Dalamud 15, ApiProbe, 20/11): no known function opens the game's report window for a player, by content id
or by name and world. The methods named « Report » are `LobbyUIClient.ReportError`, `LobbyRequestCallback.ReportError` (connection errors)
and `WKSMissionModule.ReportMission` (a cosmic exploration mission); nothing for « Complaint », « Grievance », « Abuse », « Harass » or
« Violation »; the 510 `AgentId` values hold no report agent (`Blacklist`, `Mutelist`, and the support desk's `SupportMain`,
`SupportList`, `SupportView`, `SupportEdit`, which are not a player report). Chat 2 does not offer it either. Opening it would need a
hand-made signature, which Tensho does not use (R08). So no « Signaler ce joueur » entry of Tensho's own: for a player in range,
« Game menu… » opens the game's own menu, with what the game offers there.

## Dalamud's rules (R04)

Calling the game's functions on the player's click is not automation: nothing runs without a click, nothing is sent in the player's place
(a tell is only prepared), the hook changes nothing in the message and only copies two numbers. Other players' identifiers stay in memory.

## X-660 (0.1603): the identifiers given only when everything agrees

Review of 0.1602 (I1): the identifiers went to the last message copied by order and world only. Two cases could give them to another
player: a message hidden by another plugin (Dalamud's `ChatMessageHandled`: not copied, so neither noted nor skipped, while the game may still
give its identifiers), and a tell you send (its sender link is the recipient, the identifiers the game gives may be yours).

What `AddMsgSourceEntry` gives (FFXIVClientStructs of Dalamud 15, ApiProbe, 20/11): `contentId, accountId, messageIndex, worldId, chatType`;
`RaptureLogModule.LocalPlayerContentId` is your own character's; `RaptureLogModule.GetLogMessageDetail(index, out sender, out message,
out logKind, …)` reads the game's own log line at an index (its sender as a string with the player link).

Now (`ChatSources.Resolve`, pure): given once to the message just copied, only when the kind the game gives (low seven bits of `chatType`)
is the expected line's, the game's log line at `messageIndex` has that kind and that sender (name and home world of its player link), the
world is the sender's, and the content id is not your own; else nothing, and the entries that need them stay greyed. A message hidden by
another plugin ends the wait (`ChatMessageHandled`). Each outcome is said once per session in the log (« Chat window, a sender's
identifiers: Given (kind 10). »: outcome and kind only, never a name nor an identifier).

Not established offline: that the game's log line is already written when `AddMsgSourceEntry` is called, and that `chatType` carries the
message's kind in its low seven bits. If either is not so, nothing is given (« LineUnread » or « Kind » in the log) and the entries stay
greyed: the game test says which.
