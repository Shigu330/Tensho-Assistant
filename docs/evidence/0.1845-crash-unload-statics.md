# 0.1845: the two game crashes of 22/11/2026 (« CLR error occurred », X-802)

English first, then French.

## What was read

- Two crash reports of Dalamud's crash handler and their minidumps (13:46:56 and 18:30:58, local time), both « The process was
  terminated due to an internal error in the .NET Runtime … with exit code 0x80131506 », .NET 10.0.14, Dalamud 15.0.4.1. The dumps were
  opened with the Windows debugger (cdb from WinDbg 1.2611) and SOS, Microsoft's public symbols for coreclr.dll.
- Dalamud's log of the same sessions (the lines just before each crash).
- In both dumps the exception Dalamud raised (0x12345679) comes from its hook on the runtime's event report: the runtime was already
  writing its fatal error (`EEPolicy::HandleFatalError` → `LogFatalError`). The first error under it is an access violation inside
  coreclr.dll, found on the faulting thread's stack (`!dumpstack`: « Exception Code c0000005 »).

## Crash 1, 13:46:56 (Tensho's sixth load in 20 minutes, developer mode)

- Faulting thread: a pool thread (« .NET TP Worker »), started by the runtime (`KickOffThread`). Under the access violation:
  `coreclr!RuntimeTypeHandle_GetFields`, `InvokeUtil::GetFieldValue` → `FieldDesc::GetCurrentStaticAddress`,
  `RuntimeFieldHandle_GetValue`: a static field read by reflection (`FieldInfo.GetValue(null)`).
- The log: « Load 10 s later … previous instance still alive » at 13:46:55.067, then the readers' lines, the last one at 13:46:55.074
  (« JIT warm-up's longest compilations so far »). In the code (Plugin.cs, the developer mode's continuation ten seconds after a load,
  run on a pool thread), the next statement wrote one « Earlier instance … » line per earlier instance through `UnloadWatch.Describe`,
  then read the newest earlier instance's unload state and every static field of its assembly (`UnloadWatch.Released`,
  `UnloadWatch.Statics`). No « Earlier instance » line was written: the crash is in `Describe`, 1.3 s later.
- `Describe` took each part of the earlier instance that was still alive (`WeakReference.Target`) and, to tell « shared » values apart
  (0.1195), read the static fields of its type and base types by reflection (`StaticValues`). An earlier instance is a copy of Tensho
  whose load context was unloading: that reading ran in a collectible assembly being torn down (its static storage, and the class
  initialisation of a type never used before).
- Cause: Tensho's own developer-mode diagnostic. Players without the developer mode never ran it; it ran only after a reload, with an
  earlier instance still alive.

## Crash 2, 18:30:58 (in a dungeon, no reload for 15 minutes, 23 loads in that game process, 32 plugins loaded)

- Faulting thread: the game's framework thread, in Tensho's gear set reader (`GameGearsetReader.OnUpdate` → the `Copied` handler →
  `CharacterJobs.SameContent` → `Enumerable.SequenceEqual` → `MemoryExtensions.SequenceEqual<__Canon>`), on the interface call
  `IEqualityComparer<T>.Equals`. The access violation is in `coreclr!VirtualCallStubManager::ResolveWorker` (virtualcallstub.cpp line
  1900), reading the loader module of the called object's MethodTable: that MethodTable is the GC's « Free » one (`!dumpmt`: « Free
  MethodTable »). The object called, the comparer `EqualityComparer<SavedGearset>.Default` (a static value), was a freed block of the
  managed heap: a reference to an object already collected.
- Only one TenshoAssistant.dll was in the process (`!dumpdomain`): the code that ran was the current instance, every earlier copy
  collected. The heap is not in a minidump (`!eeheap` empty): what freed the object cannot be read.
- In that same process, at 17:02:13, the diagnostic of crash 1 ran in full on an earlier instance still alive (« 488 of 497 parts
  alive », its unload state and dozens of « static » lines): the reflection on a load context being unloaded did run there, 88 minutes
  before. Both crashes touch the statics of a collectible assembly in a process where Tensho was reloaded many times.
- Not proven: the link from 17:02 to 18:30. Another plugin's native code, or a runtime defect around unloaded load contexts, cannot be
  ruled out from this dump. Tensho's own code on that path is plain managed code (lists, `SequenceEqual`).

## Leads ruled out

- The JIT warm-up (relay 180's reading): it was not the faulting thread of crash 1 (a pool thread doing reflection on statics) and
  does not appear in crash 2.
- The machine's memory: 2,193 MB free at 13:46 and 4,765 MB free with 45 GB of commit left at 18:15; an exhausted memory gives an
  OutOfMemoryException or a failed commit, not an access violation in the runtime on a valid but freed reference.
- A SQLite connection kept at unload: no frame of e_sqlite3 or of Microsoft.Data.Sqlite on any thread of either dump.

## The change (0.1845)

- `UnloadWatch.Describe` asks each part `IsAlive` only, never its `Target`: nothing of an earlier instance is taken, no static field of
  its types is read, nothing of it is run. The « shared » count of 0.1195 goes (no part is noted shared since 0.1195).
- Plugin.cs no longer takes the newest earlier instance to read its unload state and its statics (`Released`, `Statics` stay for the
  tests only, on the tests' own assembly).
- Tests: UnloadCrash1845Tests (a weak reference that counts the reads of its target: none, alive or collected; the wiring).
- To see in the game (done, below): at least six reloads in a row in developer mode without a crash (the publications of the next versions).

## Check of the reloads (23/11, relay 191's reading)

Six reloads in a row with the fix, in developer mode, in the same game process (dalamud.log, read load by load):

| Load | Time of the load | Version loaded | Earlier instance | Unloaded at |
|---|---|---|---|---|
| 32 | 02:36:37 | 0.1845.0 | 0.1844.0 | 02:50:26 |
| 33 | 02:50:28 | 0.1846.0 (first build) | 0.1845.0 | 02:52:58 |
| 34 | 02:53:00 | 0.1846.0 | 0.1846.0 | 03:16:36 |
| 35 | 03:16:38 | 0.1847.0 | 0.1846.0 | 03:29:02 |
| 36 | 03:29:04 | 0.1848.0 | 0.1847.0 | 03:42:24 |
| 37 | 03:42:26 | 0.1848.0 (« suite » commit) | 0.1848.0 | still loaded at 03:53 |

- Each one went past the moment of crash 1 (10 s after the load): its lines « Earlier instance … context collected after N full
  collection(s) since its unload, 0 of … parts alive » are written 10 s after the load, with no « static » line nor any read of an
  earlier instance still alive (all collected).
- Each unload says « SQLite connection factory released » and « process event handlers still from this copy: none ».
- No crash file (`dalamud_appcrash_*`) after the one of 22/11 at 18:30; no warning nor error of Tensho at load 37.
- Six reloads in a row without a crash: X-802's definition of « done » is met (the link between 17:02 and 18:30 stays unproven, see
  above).

# 0.1845 : les deux plantages du jeu du 22/11/2026 (« CLR error occurred », X-802)

## Ce qui a été lu

- Deux rapports du gestionnaire de plantage de Dalamud et leurs mini-vidages (13 h 46 min 56 s et 18 h 30 min 58 s), tous deux « le
  processus a été arrêté par une erreur interne du runtime .NET … code de sortie 0x80131506 », .NET 10.0.14, Dalamud 15.0.4.1. Vidages
  ouverts avec le débogueur de Windows (cdb de WinDbg 1.2611) et SOS, symboles publics de Microsoft pour coreclr.dll.
- Le journal de Dalamud des mêmes sessions (les lignes juste avant chaque plantage).
- Dans les deux vidages, l'exception levée par Dalamud (0x12345679) vient de son crochet sur le rapport d'événement du runtime : le
  runtime écrivait déjà son erreur fatale (`EEPolicy::HandleFatalError` → `LogFatalError`). La première erreur, dessous, est une violation
  d'accès dans coreclr.dll, trouvée sur la pile du fil fautif (`!dumpstack` : « Exception Code c0000005 »).

## Plantage 1, 13 h 46 min 56 s (6e chargement de Tensho en 20 minutes, mode développeur)

- Fil fautif : un fil du pool (« .NET TP Worker »), lancé par le runtime (`KickOffThread`). Sous la violation d'accès :
  `coreclr!RuntimeTypeHandle_GetFields`, `InvokeUtil::GetFieldValue` → `FieldDesc::GetCurrentStaticAddress`,
  `RuntimeFieldHandle_GetValue` : un champ statique lu par réflexion (`FieldInfo.GetValue(null)`).
- Le journal : « Load 10 s later … previous instance still alive » à 13 h 46 min 55,067 s, puis les lignes des lecteurs, la dernière à
  13 h 46 min 55,074 s (« JIT warm-up's longest compilations so far »). Dans le code (Plugin.cs, la suite du mode développeur dix
  secondes après un chargement, sur un fil du pool), l'instruction suivante écrivait une ligne « Earlier instance … » par instance
  précédente par `UnloadWatch.Describe`, puis lisait l'état de déchargement de la plus récente et tous les champs statiques de son
  assemblage (`UnloadWatch.Released`, `UnloadWatch.Statics`). Aucune ligne « Earlier instance » n'a été écrite : le plantage est dans
  `Describe`, 1,3 s plus tard.
- `Describe` prenait chaque partie encore vivante de l'instance précédente (`WeakReference.Target`) et, pour mettre à part les valeurs
  « partagées » (0.1195), lisait par réflexion les champs statiques de son type et de ses types de base (`StaticValues`). Une instance
  précédente est une copie de Tensho dont le contexte de chargement se décharge : cette lecture tournait dans un assemblage
  déchargeable en cours de démontage (le stockage de ses statiques, et l'initialisation d'un type jamais servi avant).
- Cause : un diagnostic de Tensho, du mode développeur. Les joueurs sans mode développeur ne le faisaient jamais tourner ; il ne tournait
  qu'après un rechargement, une instance précédente encore en vie.

## Plantage 2, 18 h 30 min 58 s (en donjon, aucun rechargement depuis 15 minutes, 23 chargements dans ce processus, 32 plugins chargés)

- Fil fautif : le fil du framework du jeu, dans le lecteur des gear sets de Tensho (`GameGearsetReader.OnUpdate` → l'abonné `Copied` →
  `CharacterJobs.SameContent` → `Enumerable.SequenceEqual` → `MemoryExtensions.SequenceEqual<__Canon>`), sur l'appel d'interface
  `IEqualityComparer<T>.Equals`. La violation d'accès est dans `coreclr!VirtualCallStubManager::ResolveWorker` (virtualcallstub.cpp
  ligne 1900), à la lecture du module de chargement de la MethodTable de l'objet appelé : cette MethodTable est celle des blocs libres du
  ramasse-miettes (`!dumpmt` : « Free MethodTable »). L'objet appelé, le comparateur `EqualityComparer<SavedGearset>.Default` (une
  valeur statique), était un bloc libéré du tas : une référence vers un objet déjà ramassé.
- Un seul TenshoAssistant.dll dans le processus (`!dumpdomain`) : le code qui tournait était l'instance en cours, toutes les copies
  précédentes ramassées. Le tas n'est pas dans un mini-vidage (`!eeheap` vide) : ce qui a libéré l'objet ne se lit pas.
- Dans ce même processus, à 17 h 02 min 13 s, le diagnostic du plantage 1 a tourné en entier sur une instance précédente encore en vie
  (« 488 of 497 parts alive », son état de déchargement et des dizaines de lignes « static ») : la réflexion sur un contexte en cours de
  déchargement y a bien tourné, 88 minutes avant. Les deux plantages touchent les statiques d'un assemblage déchargeable dans un
  processus où Tensho a été rechargé de nombreuses fois.
- Non prouvé : le lien entre 17 h 02 et 18 h 30. Le code natif d'un autre plugin, ou un défaut du runtime autour des contextes
  déchargés, ne s'écartent pas avec ce vidage. Le code de Tensho sur ce chemin est du code géré simple (listes, `SequenceEqual`).

## Pistes écartées

- La compilation d'avance (relevé du relais 180) : elle n'était pas le fil fautif du plantage 1 (un fil du pool en réflexion sur des
  statiques) et n'apparaît pas dans le plantage 2.
- La mémoire de la machine : 2 193 Mo libres à 13 h 46 et 4 765 Mo libres avec 45 Go d'engagement restant à 18 h 15 ; une mémoire
  épuisée donne une OutOfMemoryException ou un engagement refusé, pas une violation d'accès dans le runtime sur une référence valide
  mais libérée.
- Une connexion SQLite gardée au déchargement : aucune trame d'e_sqlite3 ni de Microsoft.Data.Sqlite sur aucun fil des deux vidages.

## Le changement (0.1845)

- `UnloadWatch.Describe` ne demande à chaque partie que `IsAlive`, jamais sa `Target` : rien d'une instance précédente n'est pris, aucun
  champ statique de ses types n'est lu, rien d'elle ne tourne. Le compte « partagé » de 0.1195 s'en va (aucune partie n'est notée
  partagée depuis 0.1195).
- Plugin.cs ne prend plus l'instance précédente la plus récente pour lire son état de déchargement et ses statiques (`Released`,
  `Statics` restent pour les tests seulement, sur l'assemblage des tests).
- Tests : UnloadCrash1845Tests (une référence faible qui compte les lectures de sa cible : aucune, vivante ou ramassée ; le câblage).
- À voir en jeu (fait, ci-dessous) : au moins six rechargements de suite en mode développeur sans plantage (les publications des versions suivantes).
