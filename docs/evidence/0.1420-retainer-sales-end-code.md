# 0.1420 : la fin des ventes des servants, lue dans le code du jeu (X-434)

Question (relecture du bloc 0.1413 à 0.1419, I1) : en 0.1415, le lien entre l'heure `lnum4` de la ligne « Selling n items until
<settime(lnum4)> » (Addon 2314) et `RetainerManager.Retainer.MarketExpire` était déduit de l'ordre des paramètres, pas lu. Quel champ le jeu
passe-t-il vraiment comme `lnum4` ?

## Sonde

`tools/AddonTextProbe` (nouvelle) : lit le client installé `ffxiv_dx11.exe` comme un fichier (rien n'est exécuté, aucun processus touché),
désassemble sa section de code (décodeur Iced, celui que Dalamud fournit) et liste le code qui charge un numéro de ligne de la feuille Addon
comme valeur immédiate, avec les instructions autour ; `--struct=` donne les décalages des champs d'une structure de FFXIVClientStructs
(métadonnées). Client 7.58 (jeu 2026.11.03.0000.0000), le 2026-11-15 :

```
AddonTextProbe --struct=FFXIVClientStructs.FFXIV.Client.Game.RetainerManager+Retainer 2314,2315,967,2317 --before=260
```

Décalages de `RetainerManager.Retainer` (FFXIVClientStructs de Dalamud 15.0.4.0) : `0x28 Available`, `0x30 Town`, `0x31 MarketItemCount`,
`0x34 MarketExpire` (32 bits), `0x38 VentureId`, `0x3C VentureComplete`.

## Ce que le code du jeu montre

Une seule fonction choisit entre les lignes 2314, 2315, 967 et 2317 (adresse relative `0xE377E5` et suivantes ; une deuxième, `0x1A8F52C`,
fait de même pour une autre fenêtre). Le registre `rsi` y pointe sur un servant (`RetainerManager.Retainer`) :

- elle empile les paramètres de la ligne, dans l'ordre, après le nom (`lstr1`) : `movzx eax,byte [rsi+30h]` (ville, `lnum2`),
  `movzx eax,byte [rsi+31h]` (nombre d'objets en vente, `lnum3`), `mov eax,[rsi+34h]` (`lnum4`, l'heure passée à `settime`), puis les
  heures et les minutes restantes de la tâche (`r15d` divisé par 60, `lnum5`, et son reste, `lnum6`) ;
- puis elle choisit la ligne : `cmp byte [rsi+28h],0` (servant indisponible : 0x906) ; `cmp byte [rsi+31h],0` (des objets en vente :
  0x90A = 2314, 0x90B = 2315, 0x90C, 0x3C7 = 967 selon la tâche ; aucun : 0x90D = 2317, 0x90E, 0x90F, 0x3C8).

L'heure que le jeu écrit après « until » / « jusqu'au » est donc le champ `+0x34`, `MarketExpire`, tel quel ; la ligne n'est choisie avec une
heure que si `+0x31` (`MarketItemCount`) est au-dessus de 0. C'est exactement ce que Tensho lit (`RetainerStates.SalesEnd`, depuis la même
lecture `RetainerManager`). Le jeu n'en montre que le jour ; Tensho montre la même heure à la minute et sonne à cette heure.

## Où chaque valeur est rangée (0.1428, X-437 M1)

Sortie brute de la sonde gardée : `docs/evidence/0.1420-retainer-sales-end-probe.log` (la fonction entière depuis son début, `0xE3728C`,
et les décalages de `RetainerManager.Retainer`). Elle montre la place de chaque valeur dans les paramètres de la ligne, pas seulement
l'ordre des lectures : la fonction crée une liste vide à `[rsp+48h]` (`movdqu [rsp+48h],xmm0`, sa taille `[rsp+68h]` à 0), puis y ajoute
en fin, dans cet ordre : le nom (`lea rax,[rsi+8]`, `_name` à `0x08` ; ajout écrit en ligne, `inc qword [rsp+68h]`), la ville
(`[rsi+30h]`, même ajout en ligne), le nombre d'objets (`[rsi+31h]`), l'heure (`[rsi+34h]`), puis les heures et les minutes restantes
(`r15d`), ces quatre derniers par `lea rcx,[rsp+48h]` puis `call 00000001401EAFC0h`. Le quatrième paramètre (`lnum4`) est donc
`[rsi+34h]`, `MarketExpire`, par sa place dans la liste. Le test `Review1428Tests` refait ce compte sur la sortie brute.

## Ce qui reste à voir en jeu

Rien pour le lien entre le champ et la date du jeu. L'essai de 0.1410 et 0.1411 (la date du tableau de Tensho égale le jour de la liste des
servants) reste dans la campagne comme contrôle ordinaire.

# 0.1420: the end of the retainers' sales, read in the game's code (X-434)

`tools/AddonTextProbe` (new) reads the installed client as a file, disassembles its code section (Iced, as shipped with Dalamud) and lists the
code that loads an Addon row id as an immediate value. The one function that picks the retainer list line (2314, 2315, 967 or 2317; relative
address `0xE377E5`) pushes, after the name, `byte [rsi+30h]` (`lnum2`, town), `byte [rsi+31h]` (`lnum3`, item count) and `dword [rsi+34h]`
(`lnum4`, the time given to `settime`), `rsi` being a `RetainerManager.Retainer` (offsets: `0x30 Town`, `0x31 MarketItemCount`,
`0x34 MarketExpire`); a line with a time is picked only when `[rsi+31h]` is above 0. The game's « until » date is the day of `MarketExpire`,
the very value Tensho reads. Nothing left to see in the game for that link. The probe's raw output is kept
(`0.1420-retainer-sales-end-probe.log`, the whole function): it makes an empty parameter list at `[rsp+48h]` and appends, in this order, the
name (`[rsi+8]`), the town (`[rsi+30h]`), the item count (`[rsi+31h]`), the time (`[rsi+34h]`) and the hours and minutes left (`r15d`):
`lnum4` is `[rsi+34h]` by its place in the list, counted on the raw output by `Review1428Tests` (0.1428, X-437 M1).
