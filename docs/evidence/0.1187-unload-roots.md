# 0.1187 — what keeps an unloaded instance alive (X-01 C1.3)

Question: at 0.1185 and 0.1186 the log said « previous instance still alive » ten seconds after a load, after a full collection
(0.1186-load-measures.md). What holds the load context of an unloaded Tensho, and what does it cost?

## 1. Trial out of the game (2026-11-12, .NET 10.0.14, no game, no Dalamud)

A small host loads a « victim » assembly in a collectible load context, calls one scenario in it, unloads the context, keeps a weak
reference to it and collects up to 12 times (`GC.Collect` + `WaitForPendingFinalizers`). One process per scenario. The victim holds a
settings class (a dictionary, a list, an enumeration, a nested class) and one method per scenario. Newtonsoft.Json is the file Dalamud
ships (Hooks\dev\Newtonsoft.Json.dll), loaded in the default context as in the game, except for the « private copy » rows.

| Scenario in the unloaded context | Context after 12 collections |
|---|---|
| nothing (a settings object built) | collected (2 collections) |
| Newtonsoft: `SerializeObject` + `DeserializeObject` with Dalamud's settings (TypeNameHandling.Objects) | **still alive** |
| Newtonsoft without settings | **still alive** |
| Newtonsoft, private copy loaded in the victim's own context | **still alive** |
| `TypeDescriptor.GetConverter(type)` alone (what Newtonsoft calls for each type it writes) | **still alive** |
| the same, then `TypeDescriptor.Refresh(assembly)` or `Refresh(type)`, or the runtime's own cache-clearing handler | **still alive** |
| System.Text.Json without options (`JsonSerializer.Serialize(value)`) | **still alive**, also after other JSON work in the host |
| System.Text.Json with options owned by the victim (static, or new at each call, with or without a converter) | alive at first; collected once the host did other JSON work more than a second later |
| FileSystemWatcher disposed, `Task.Run` finished, `Task.Delay(200).ContinueWith` run, a thread finished, HttpClient disposed, Regex (also compiled), enumerations, LINQ, expressions compiled, DynamicMethod | collected (2 or 3 collections) |

Reading:

- **Dalamud's settings API is a root, for every plugin.** `GetPluginConfig` and `SavePluginConfig` read and write the settings object with
  Newtonsoft.Json; Newtonsoft asks `System.ComponentModel.TypeDescriptor` for a converter for each type it meets, and TypeDescriptor keeps
  the type in static tables of the shared runtime, with no public way to take it out. The types of the settings stay referenced, so the
  load context of the unloaded plugin stays alive for the life of the game process. A private copy of Newtonsoft does not change it
  (the table is the runtime's). Tensho also calls Newtonsoft itself for the off-thread save (0.1164).
- **System.Text.Json without options is a second root**: the shared default options cache the types they met. With options owned by the
  plugin the cache dies with the plugin (after the runtime's own cache of member accessors expires, on the next JSON work in the process).
  Tensho has about 35 such calls without options (BeastTeams, AchievementProgressStore, GitHubExchange, ExchangeV3, SeenPrices…).
- Timers, tasks, threads, watchers and HTTP clients that are finished or disposed are not roots.

So « previous instance still alive » is expected in the game for any plugin with settings: the context cannot be unloaded as long as the
settings go through Dalamud's API. What matters is what the living context still references.

## 2. What the living context held: the whole instance (fixed in 0.1187)

A static field lives as long as its load context. Four static hooks were given by the plugin's constructor as closures and never emptied:
`CompetitiveGate.Developer`, `CompetitiveGate.SlowSubscription`, `WeatherCatalog.StoryWeatherConfirmed` (and `CompetitiveGate.Changed`,
emptied by the watcher's own release only). The constructor is one method: its closures share one object that holds every captured local
(the settings, the window, the services, the catalogues). Through these hooks each unloaded instance stayed reachable, whole, at every
reload: this is the growth of the heap and of the full collections with the reload's rank (lenteurs of 12/11, C1).

0.1187 empties the hooks last at unload (`CompetitiveGate.ForgetInstance`, `StoryWeatherConfirmed=null`, `MapLiveReader.Log=null`), takes
off the framework what a reader would have left subscribed (`CompetitiveGate.ReleaseAll`, counted in the log), and a test (cliquet) refuses
a new static hook that the unload does not empty. Behaviour test: an object captured by the hooks is not collectible while they are set,
and is collected once they are emptied (UnloadRoots1187Tests).

## 3. Measure in the game (0.1187 on, developer mode)

Each instance notes weakly, at its unload, the plugin object, the window and their fields that hold objects of the plugin's own code
(`Diagnostics.UnloadWatch`, a process-wide slot made of runtime types only). Ten seconds after each load, one line per earlier instance
(four at most): « Earlier instance 0.1187 loaded at HH:mm:ss: context alive, N of M parts alive: … ». Nothing is collected or forced: an
instance unloaded a few seconds before may still be alive for lack of a collection; the instances two or more loads back tell.

### Readings of 2026-11-12 (game running, character in town, developer mode; one load per version published)

| Read at | Instance | Line |
|---|---|---|
| 21:32:37 | 0.1187 loaded 21:29:37, unloaded 21:32 | context alive, 330 of 338 parts alive, after a full collection (3.3 s of pauses): the static hooks emptied were not the only root |
| 21:54:10 | 0.1188 loaded 21:49:21 | 463 of 471 alive; collected: the four fields the unload itself sets to null and four of the window's; « registrations disposed: True, releases left: 0 »; statics of its assembly: tables of data only (no delegate with a target, no service) |
| 22:05:42 | three instances two loads back or more | hubs emptied (512, 562 and 707 fields), no error in the log |
| 22:20:03 and 22:31:47 | 0.1188 loaded 21:49:21 and 21:54:00, hubs emptied | 78 of 471 alive: `plugin`, `window` (= `plugin.mainWindow`), `plugin.dataCache` (= `window.dataCacheStore`), `locals.CS$<>8__locals1` (the closure of the constructor's outer scope: its parameters and this), and 72 fields of the window that hold shared empty lists (alive with the context, not with the instance). No captured service of the constructor (`locals.*`) is alive |

Reading: the unload finishes and releases everything it registered; nothing static in the plugin holds an instance. Something outside the
plugin's fields and captured locals still holds, directly, the window, the data cache and an object that reaches the outer closure (the
localisation manager's warning callback is the only lambda of that scope). Emptying the hubs lets 393 of the 471 noted parts go: in
developer mode the growth per reload is now what that root holds, not the whole instance (the heap figures of the load lines are the
whole game process's and do not show it: 8.1 to 8.5 GB over these loads). From 0.1191 the outer closure is emptied too; from 0.1192 the
plugin's own objects behind the hubs are noted by path, three levels deep, so that the next lines name the chain the root holds.

## 4. Left

- Name the root: read the « Earlier instance … hubs emptied … parts alive » lines after two more reloads of 0.1192 or later (paths such as
  « locals.service.field » or « window.field→Target »); suspects not ruled out: an object built inline in the constructor (a window, a
  bar entry, a command) that Dalamud still references, a pending task of the data cache.

- The context itself: settings read and written without Newtonsoft (a format change of the settings file, the user's data: its own
  version, with its behaviour tests), and the JSON calls without options given the plugin's own options. Gain: code and static tables of
  each unloaded instance; to weigh against the risk once the measure of section 3 says what an unloaded instance still holds.
