# 0.1660: a player's menu in the Tensho chat window, never empty; the tell by name (X-679, X-681)

## The report (X-679, the user's report of 20/11 around 21:50, three pictures)

Right-click on a player's name in the Tensho chat window, « Yell » and « Say » messages, even a new one of 21:35 (after the load of 21:32):
only Tensho's entries (copy, hide, put forward), none of the game's (Tell, Reply, Invite, Adventurer Plate, Target, the game's menu), while
the game's own chat offers them. A new « Say » of 21:36 had them.

## What the log says (dalamud.log of 20/11, kept as dalamud.old.log and dalamud.log)

- The hook on `RaptureLogModule.AddMsgSourceEntry` is set in the plugin's constructor (`Plugin.cs`, `registrations.Register(...)`, not
  deferred) and enabled in `ChatPlayerActions`' constructor: nothing starts minutes later.
- Each outcome of the identifiers is said once per session. From the first load of 20/11 to 23:58, the only outcomes ever said are
  « Given » (kind 10, Say: 21:14:24, 21:36:40; kind 11, Shout: 21:19:59, 21:39:43, 21:48:50, 23:28:37); never « Kind », « Line »,
  « LineUnread », « World », « Own » nor « NoIdentifiers ». The first « Given » of each session comes at the first player's message
  (21:32:06 load, first given 21:36:40; 21:38:33, 21:39:43; 21:48:06, 21:48:50): the measure of a late start is the first message.
- Before 0.1658, « NotWaiting » (identifiers that no message waited for) and a failure to read them were never said; since 0.1658 they are,
  once, with the delay of the first call after the load. The loads of 0.1658 and 0.1659 (23:34, 23:42, 23:54) had no player's message yet.

## The causes found

1. Fixed in 0.1658: the chat history put back after a reload numbers every line again; the senders kept by number were lost for every
   message received between the load and the history (21:32:06 to 21:32:31).
2. Found here: the menu drew the game's entries only when the message itself had a source (`ChatSenders.For(id)`), and drew nothing at all
   otherwise (the comment promised greyed entries). A message has no source of its own when it is from the history on disk, when it was a
   repeat folded into an older copy (« Fold repeats »: the menu is the first copy's, an older line), when its line was renumbered, or when
   the game's chat event gave no player link to note (then it never waited for its identifiers: « NotWaiting »). Every such message of a
   player showed none of the game's entries, even a new one.

## What Tensho does now (0.1660)

- The identifiers are the character's, not the message's: the last ones given to a player (name and home world) serve their other
  messages too (`ChatSources.Find`): by the message, else by the same player, else the message's own source without them, else the player
  its text names (« Name@World », glyphs taken off; no world written: the world you are on). Never another player's (another name or another
  world gives nothing), never your own character's (the game's own id is refused), in memory only, bounded, cleared with the messages.
- No sender at all: the entries are shown greyed, each with the reason in its tooltip (no sender, no identifiers, no account identifier,
  not near you); never an empty menu. Your own lines and what no player says have none.
- The log says once per session where a menu found its sender (« Message », « Player », « MessageOnly », « Named », « None », with the
  kind): « Named » for a new message would show the chat event gave no player link for that kind.

## The tell by name (X-681, the user's request of 20/11 around 21:45: « Tell, can't it be done with the name? »)

FFXIVClientStructs (Dalamud 15, ApiProbe of 21/11): `RaptureShellModule.SetContextTellTarget(name, worldName, worldId, accountId,
contentId, reason, setChatType)` fills the shell's tell target (`TellName`, `TellWorld`, `TellWorldId`, `ContentId`, `AccountId`,
`TellReason`) and sets the typing box to a tell; it sends nothing. A tell typed « /tell Name@World » gives the game only a name and a world,
so the game sends tells by name and world without knowing the player's identifiers; Tensho now calls the same function with the identifiers
it has (0 when it has none). The game's `ChatChannel` of FFXIVClientStructs only names Say (1), Party (2) and Alliance (3): no other function
sets a tell by name. Not read in the game's code: that a tell set with identifiers 0 is sent like a typed « /tell ». The game test says so
(Tell on a message without identifiers, write and send: the tell arrives); if not, the entry goes back to greyed without identifiers.

Only on the player's click (R03.3: the typing box is set, the player writes and sends), never during a cut (PvP, ranked contents: checked
at the click and at the next tick, R03.2). The reply to a tell is the same. A party invite was already possible by name on your world
(`InfoProxyPartyInvite.InviteToParty`), target and the game's menu by the character in range; the adventurer plate and the mute list need the
game's identifiers (`AgentCharaCard.OpenCharaCard(contentId)`, `AgentMutelist.Add(accountId, contentId, …)`) and stay greyed with the reason.
