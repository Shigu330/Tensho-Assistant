## API (Raphael.Net/Solver.cs, SolverInput.cs, SolverConfig.cs)

- Entrée : CP, durabilité, progression et qualité visées, gains de base de progression et de qualité, niveau, charges
  de Stellar Steady Hand.
- Options : `Adversarial`, `BackloadProgress`, `AllowNonMaxQualitySolutions`, `ThreadCount`, `LogLevel`.
- Rappels : solution finale (`OnFinish`), solutions intermédiaires proposées (`OnSuggestSolution`), progression (`OnProgress`),
  journal (`OnLog`). `Cancel()` lève un drapeau natif ; `Dispose()` annule, puis attend la fin.
- `Solve()` bloque son thread : il faut l'appeler hors du thread du jeu, dans une tâche annulable.

## Risques et limites

- **Code natif dans le processus du jeu** : une erreur dans la bibliothèque Rust ferait planter le jeu ; un try/catch .NET ne
  l'attrape pas. Craftimizer en a l'usage depuis plusieurs versions ; c'est le même binaire.
- Mémoire et durée : la README de raphael-rs ne donne pas de chiffres (recherche par séparation et évaluation, A*, Pareto). Il faut
  les mesurer sur des recettes de haut niveau. Garde-fous : nombre de threads réglable, annulation, un seul calcul à la fois.
- **A-04 (suggestions pendant la synthèse)** : Raphael part de l'état initial d'une recette. L'API ne prend pas l'état en cours
  (progression et qualité déjà acquises, Inner Quiet, Innovation, Veneration, Waste Not, condition).
  - Un nouveau calcul en cours de synthèse ne pourrait viser que la progression et la qualité **restantes**, avec la durabilité et
    les PC actuels, sans les effets actifs : c'est une approximation.
  - La version exacte demande le solveur C# de Tensho (CraftSolver, qui part d'un état simulé) ; Raphael reste réservé aux macros
    complètes (A-03).
- Validation : toute macro proposée par Raphael serait rejouée dans CraftSimulation (comme CraftSolver aujourd'hui) ; un écart est
  signalé et la macro n'est pas proposée.
